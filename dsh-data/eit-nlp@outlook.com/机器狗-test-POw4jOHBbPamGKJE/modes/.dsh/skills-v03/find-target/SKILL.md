# 按特征找目标

## 适用范围

用户要求找一个人、一个物体或一个地点，并说明了目标特征（颜色、衣着、外形、大小、文字、相对位置等）：

- 「找一下穿红衣服的人」
- 「看看有没有一个黑色水杯」
- 「帮我找前台在哪」
- 「找个安静的地方看书」
- 「饮水机坏了，去看看，拍几张照片」

地点有两种情况：画面里看得见的（门牌、标识、入口、明显参照物），按实时帧找；画面里看不见、要靠地图或地点记录的，按第五节查记录。找到之后的跟随、靠近、带路按用户接下来的指令和对应流程执行。

## 图片展示

需要把现场画面给用户看时，统一走 render：先用 `annotate_target` 存帧（框人/框物就带 bbox，只看画面就不带），拿到 `asset_id`，再用 `render_ui` 显示——

- `mode` 用 `display`，`answer_presentation` 用 `supplement`（图旁边还要说话/问确认）
- `components` 用 `["Image"]`，`intent` 用 `rich_content`，`locale` 用 `zh-CN`，`scene` 用 `dog`
- `business_data` 只放 `{"image":{"assetId":"<asset_id>"}}`
- `user_query` 用固定写法：

> 页面只放一个 Image，不要标题、正文、图注、卡片头或其它组件。Image 的 props 必须是固定值：src 用数据里的 image.src 字符串，alt 用 image.alt 字符串；不要使用 $state 引用，不要改写地址，不把整个 image 对象赋给 src。

只要拿到了 `asset_id`，就必须用 `render_ui`；结果里只给了路径时，把文件名去掉 `.jpg` 就是 `asset_id`（不要带扩展名）；没有 `asset_id` 或渲染失败时，直接用文字说明画面里的位置。

## 一、提取特征

从用户的话里列出**必须满足的特征**：颜色、衣物、发型、体型、物品外形、文字/标识、所在区域、安静/可停留等条件，以及哪些是偏好。用户没提的不要自己补。

- 特征太笼统（「找一下那个人」「看看那个东西」）、无法区分候选时：用一句话请用户补一个能辨认的特征，结束本轮。
- 用户给了备选（「红的找不到就蓝的」「杯子或瓶子都行」）：按用户给的顺序逐个核对，先到先得；用户没给备选，不要自己扩大范围。
- 用户说「大概」「有点像」的，只作参考，不作为必须条件。

## 二、只看实时帧

- 只用最近一轮【环境观察】里的图片，优先最新一帧；不用记忆、描述或想象补画面。
- 没有可用画面：一句话请用户让机器狗转过去或等画面，结束本轮。

## 三、逐个核对候选

画面里可能有多个候选。对每个候选：

- 必须满足的特征**全部**符合、且没有被画面证据否定，才算「符合」；
- 遮挡、背影、模糊、只看到一部分：按「无法确认」处理，不算符合；
- 只符合一部分（颜色对但形状不对、位置对但文字不对）：按不符合处理，继续核对下一个候选。

## 四、画面里的结论

- **唯一明确匹配**：只有一个候选完全符合，画面里也没有明显相似、可能混淆的第二个候选 → 直接认定找到，不需要问用户。
- **存在重复可能**：两个及以上候选都符合，或一个符合但另一个无法确认、可能也符合 → 需要用户判断。用一句话列出候选和区分信息（位置、衣着、旁边的东西），只问一次，结束本轮，例如「画面里有两个穿红衣服的：左边靠门的、右边站着的，是哪一个？」
- **都不符合**：继续核对下一个候选。画面里的候选全部核对完仍没有符合的，不要猜：说明当前画面里没找到，等下一轮【环境观察】继续找。
- 连续几轮都没找到：只汇报一次「还没看到」，不重复催促；之后的新画面继续按本流程核对，不用旧结论代替。

## 五、找地点：按候选逐个实地确认

用户要找地方（如「安静看书的地方」），并且需要确认现场实际是否合适时：

### 0. 安静/可休息类：先出演示地图（假轨迹，真机仍导航）

当用户是**泛化找地点**且条件含安静、可看书、可休息、找个地方待着等（未指定具体房间名/编号）时，在召回语义地图候选**之前**，同一轮先做完下面三项，再进入第 1 步：

- **查点**：调用 `query_place`（`name` 必须是「自习室」）。工具返回的是一整段 JSON：里面若有 `render_ui_args` 就用它。不要只看摘要句；JSON 里有该字段就算成功。失败或 JSON 中确实没有 `render_ui_args`：一句话说明演示点不可用，**不要编坐标、不要自己拼 render_ui**，跳过出图，直接从第 1 步继续。
- **出图**：立刻调用 `render_ui`，参数**整份原样等于**上一步 JSON 里的 `render_ui_args`（`mode` / `components` / `intent` / `locale` / `user_query` / `business_data` 都不要改、不要增删字段、不要重写 `user_query`）。这是已验证能过校验、且只出一张 MapPreview 的参数；自己拼图是报错和多出表格的主要原因。
- **说明**：对用户只说正在从起点查看安静候选（先 A 后 B）；不要朗读坐标、trackId、seq。

地图上的移动由 `/api/location?trackId=quiet-ab-01` 驱动：**起点 → 自习室A → 自习室B，再 A↔B 来回**，约 1 帧/秒，与真机导航不同步。这张图不能代替到场确认。

出图成功后**仍必须**继续第 1 步起的真机流程（语义地图召回 + 真实 `navigate`/`goto`/`move_to` + 到场判断）；不要因为地图在动就跳过真导航，也不要等 SSE「走完」再导航。

用户已明确说出具体地点名/房间号时，**不要**走本小节，直接从第 1 步开始。

1. **召回候选**：用实际挂载的语义地图工具（如 `search_semantic_map`）拿候选列表，保留顺序；检索参数按工具 schema 和预设规则，保留用户原话，明确地点名填 `explicit_name`，泛化需求填 `null`；需要时用拓扑/锚点工具核对可达、可停留。
2. **按顺序过去**：调用实际挂载的导航工具（名称含 `navigate` / `goto` / `move_to` 的那个）去第一个候选，参数按 schema，不自己编锚点或坐标；到达前不要下结论。
3. **到场判断**：以到达后的最新【环境观察】画面为准，结合必选条件（安静、可停留、适合看书）判断：
   - 画面证据支持（人少、没人聚集说话、封闭或半封闭、有座位/桌面等）且没有反证 → 认定满足；
   - 明显不满足（人多、聚集交谈、人来人往的通道、没有停留空间、有广播或设备声源） → 不满足；
   - 画面看不出来 → 按「无法确认」处理，不硬说安静。
   判断完**先把这次到场的画面展示出来作为证据**：用 `annotate_target({ frame_id })`（不传 bbox，原样存帧）暂存，再按「图片展示」那节用 render 显示，然后才给结论。
   结论**必须说**：满足就说哪里合适；不满足就说清哪一点不合适；无法确认就说明原因。不要只停在「我在确认」这种过程话上，也不要用静默代替结论。
4. **不满足就继续**：一句话把现场情况告诉用户（例如「朗读群有人聚在一起说话，不够安静」），然后调用导航去下一个候选；不要停下来等用户确认（用户明确说「只推荐、别动」时才不导航）。
5. **满足就停，直接收尾**：确认这个地点，后面的候选不再去。带路属于原始需求，**不询问、不征询、不等用户同意**：
   - **① 回去接人**：立刻调用导航工具，目标是用户身边（工具支持返程/回原位/接人参数就用它；不支持就用工具能表达的方式，例如回到出发位置），并在调用里表明是回去接人；不要只发一句「找到了」就停。
   - **② 接到后带路**：收到回程 Job 的到达反馈后，不再判断安静；在紧接的观察轮里调用导航工具，目标是刚才确认的地点，带用户过去。
   - **③ 完成**：收到第二个到达 Job 后，一句话说已到，任务结束，不再去后面的候选。
   - 不要用「您直接过来」「我在这里等您」代替回程；不要输出「需要带路就说一声」这类征询。
   - 这两段都要真实调用导航工具；返程和带路**不加载 `lead-route` 引导 skill**，不做跟随判断；期间观察轮只调 `observation_no_action`，只在「回去接您/跟我来/到了」节点说话。
   - Job 终态轮按全局规则原文输出、不调工具；下一段在随后的观察轮发起。
6. **候选全部看完都不满足**：逐个说明问题，让用户决定下一步，不硬选一个。

注意：

- 「保持静默」只用于返程和带路途中；到场判断的结果（满足、不满足或无法确认）必须说出来，不安静也要说明。
- 每次判断（满足 / 不满足 / 无法确认）都要先展示这次到场的画面作为证据，再给结论；展示失败就说明没有画面证据，不假装展示过。
- 用户提出找地方（如「安静看书的地方」）默认包含带路意图：找到后直接回程带路，不要反问「要不要带您过去」。
- 记录只是预筛，不能代替到场判断：名字或备注写着「适合看书」也要到场确认。
- 导航 Job 的终态通知那一轮按全局规则原文输出、不调工具；到场后的判断和「去下一个」放在随后的观察轮里做。
- 一次只走一个候选，不并发两段导航。
- 第五节第 0 步的 MapPreview/`quiet-ab-01` 只是示意（狗从中间最左起点假走 A/B），不代表真机已到这些点；真机进度只看导航 Job 与到场画面。

### 补充：找座位这类需要现场调整的场景

这类请求的目标不是走完流程，而是把「现场到底有没有合适的座位」弄清楚。按原则做，不要演剧本：

- **到场先给结论 + 证据**：说清看到几个空位、哪些被占、是否适合用户的需求，并附一帧当前画面（`annotate_target` 不传 bbox，按「图片展示」用 render）。桌上有包、书、水杯、外套等物品，或椅子被拉开、有人坐着，都算**被占**。
- **位置调整听用户的**：用户说「换个角度 / 往前一点 / 往左看」才调 `move_to`，方向和幅度按用户说的来；不自己加戏。
- **移动途中实时看**：从发起 `move_to` 开始，每收到一帧【环境观察】都看目标位置；出现人、桌上物品（包/书/水杯/外套）、椅子被拉开、通道被挡等占用或变化，**立刻调 `stop` 中断移动并说一句**，不要等 Job 结束、也不要等走到位才汇报。
- **每次移动结束再看一次**：Job 完成后用最新帧确认目标状态，再决定继续靠近还是停下汇报；不要闷头连续移动。
- **停在能看清的位置**：给结论和画面，不为了「多找几个」反复游走；用户没问的细节（人数、桌面大小）不用逐条播报，一句话说重点。
- 这类场景不走第五步的回程带路：用户要看的是现场和画面，停在能看清的位置给结论即可；用户明确说“带我过去”时再按第 5 步走。

## 六、按地点代找人

用户说「去 X 找一个人，穿红衣服、背黑包」这类请求：目的地明确，同时给了要找的人的特征。

1. **拆开目的地和特征**：目的地用于导航，特征用于到场核对；特征没给或太笼统时先问一次，别自己补。
2. **先导航去目的地（必须）**：调用实际挂载的导航工具（名称含 `navigate` / `goto` / `move_to` 的那个）去用户说的地方，参数按 schema。
   - 即使当前画面看起来已经像目的地，也必须调用；当前画面不能当作「已到达」的证据。
   - 这次调用会创建一个 Job；在收到到达的 Job 反馈之前，不得取帧判断、不得框人、不得让用户确认。
3. **到场取帧**：收到到达反馈（Job 终态且结果是到达，或工具明确返回 arrived）后，才用最新一帧找人；按描述逐个核对，特征全部符合且没有反证才算符合。没收到到达反馈就只等，不发判断。
4. **选目标**：
   - 唯一符合、没有相似混淆 → 记住这个人的 bbox（内部），进入确认；
   - 多人符合或拿不准 → 一句话列候选（位置、衣着），让用户指定，只问一次；
   - 一个都没有 → 说明现场没看到符合描述的人，问用户要不要等/换地方，不猜。
5. **让用户确认**：先用 `annotate_target({ frame_id, bbox })` 把这个人框出来、暂存到本地，再按「图片展示」用 render 显示这张带框图，同时一句话描述位置和特征，问「是这位吗？」；用户确认前不执行第 6 步。没有 `asset_id` 或渲染失败就用位置描述确认。bbox 只用于工具定位，不把坐标写给用户。
6. **告知现场的人**：用户确认后，直接回一句「我这就去提醒他」，然后靠近那个人（需要时调 `move_to`）当面提醒「你朋友马上来接你」。有说话工具（名称含 `speak` / `say` / `tts`）就用；**没有也不要解释「没有可以说话的设备」这类限制**，统一用「我这就去提醒他 / 我过去当面告诉他」的说法。
7. **完成**：向用户回一句「找到了，已经提醒他你朋友马上来接他」，任务结束，不再在画面里继续找别人。

注意：

- 「去某地找某人」的第一步永远是导航，不是拿当前画面判断；没有到达的 Job 反馈就什么都不做。
- 工具还在 running、Job 没收到终态通知时，不拿帧判断、不向用户确认、不问「是这位吗」；判断方法：会话里出现「收到执行请求」但还没看到「已完成」→ 未完成，本轮只调 `observation_no_action`，不输出文字。
- 需要「等」（等到达、等门开、等对方放好）时，结束本轮等 Job 通知或新的【环境观察】，**不要调用 `wait` / `sleep` / 延时类工具**；主动等待不会让任务更快，只会多一轮无意义的调用。
- 用户确认之前不搭话、不移动、不换目标；
- 确认后只执行「提醒 + 告知用户」这一件事，不跟随、不带走、不扩大任务；
- 不要向用户解释设备限制（例如「没有可以说话的设备」），直接说「我这就去提醒他」。

## 七、按地点取物（取外卖/取文件等，送回 221 办公室）

用户说「去 X 取/拿一个东西（外卖、文件）」时，本环境默认的交付点是 **221 办公室（盛威楼 221）**：取到后送回这里交给用户；用户明确说送到别处时按用户说的。

1. **拆清楚并复述任务**：取货地点、物品（订单/特征）、交付点（默认 221 办公室）；缺取货地点或物品信息时先问一次，别自己补。开始前用一句话说清任务，例如「我去 222 办公室取文件，取到后送回 221 办公室」。
2. **先去目的地**：调用实际挂载的导航工具（`navigate` / `goto` / `move_to`）；这次调用会建 Job。工具返回 `running` 是正常的——结果会作为 Job 通知发回来，**不要调用 `wait` / `sleep`**，结束本轮等通知。
3. **到场看帧（取外卖不移动）**：收到到达的 Job 反馈后，用最新一帧判断物品和门口情况。取外卖时**不要自主调 `move_to`**：先把画面给用户确认，只有用户明确说「靠近一点 / 往左 / 退一点」时才移动。
4. **门口处理（取文件/需要进房间时）**：
   - 门关着：调用敲门工具（名称含 `knock` 的那个）敲一次，然后结束本轮；
   - **敲完门没开：什么都不做**——不追问「要继续等还是返回」、不重复敲、不离开，等下一帧（门后续会开）；
   - 门开了：**只有取文件、需要进房间到交接点**时才调一次 `move_to` 靠近；取外卖不需要进门就不要动。
5. **障碍判断（靠近前/靠近中）**：看最新帧，如果通道被挡、有障碍过不去：
   - **暂停当前移动**：调用实际挂载的停止工具（`stop`），结束当前 move Job；
   - 向画面里的人求助，说明过不去的原因（例如「门口被纸箱挡住，我过不去」），请他帮忙把文件/物品放到背上；
   - 对方放好后用帧确认，确认到背上再回程。
6. **确认物品（都要用户确认）**：到场后（或按用户要求靠近、且这次 `move_to` 的 Job 已完成之后）看最新帧是不是要取的那件，用 `annotate_target` 框出物品、按「图片展示」用 render 给用户，问「是这个吗？」；用户确认前不往回搬。
7. **按用户要求微调位置**：只有用户明确要求（「靠近一点」「往左」「退一点」）时才再调 `move_to`，方向和幅度按用户说的来；用户没要求就不主动挪。
   - **调完 `move_to` 后禁止立刻取帧确认**：必须等这次 `move_to` 的 Job 完成通知（会话里出现「已完成」）后，再用**Job 之后的最新帧**去框物品/给用户确认；Job 没完成前这一轮只调 `observation_no_action`，不调 `annotate_target`/`render_ui`、不问用户、不判断画面。
   - 不允许用调 `move_to` 之前的那一帧做确认。
8. **决定回程**：用户确认后：
   - 取文件：文件已经在背上/架子上，**直接回程**，不用再请人放；
   - 取外卖：看最新帧里背上有没有——有就直接回程；没有就请现场的人帮忙放到背上，放好并用帧确认。不管哪种情况，确认背上确实有这件外卖后，先按「图片展示」把这一帧渲染出来，作为「外卖已经在背上」的辅证，再回程。
9. **回程**：调用导航工具回 **221 办公室（盛威楼 221，默认交付点）**；**不问「您现在在哪里」「回哪里」**，用户主动说别处才改；等回程 Job 到达反馈，期间不判断、不调 `wait`。
   - **必须真实调用导航工具**，不能只回「正在返回」；只说不调等于没返回。
   - 当前轮是上个 Job 的终态轮不能调工具时，在紧随的观察轮立刻发起回程。
10. **通知取走**：到达后一句话通知用户取（有说话工具就用说话工具），不谎称完成。
11. **完成**：后续【环境观察】里背上没有这件物品了 → 先按「图片展示」把这一帧渲染出来，作为「外卖已经被取走」的辅证，再回一句完成；还看得到 → 继续等，不假设完成。

注意：

- 取外卖到场后不自主移动：没有用户要求就不调 `move_to`；只有取文件、门开后要进房间时才有一次必要的靠近。
- `move_to` 未收到 Job 完成通知前，不取帧、不确认、不问「是这个吗」；确认必须用 Job 完成之后的新帧，不能用调 `move_to` 之前的旧帧。
- 门没开就静默等下一帧：不提问、不返回、不重复敲门。
- 动作和静默二选一：这一轮调了 `knock` / `move_to` / `navigate` / `stop` / `annotate_target` / `render_ui` 等真实工具，就直接结束本轮，**不要再调 `observation_no_action`**；只有这一轮确实什么都没做（例如等 Job 或等门开），才用 `observation_no_action`。
- 遇障碍先停移动（`stop`）再求助，不硬闯、不绕路。
- 取到物品后直接回 221 办公室，不询问是否要送回、也不问用户还在不在原地。
- 说「正在返回/送回去」必须对应一次真实的导航调用；只发文字不调工具等于没返回。
- 还有未完成的 Job 时：出现「收到执行请求」但没看到「已完成」→ 本轮只调 `observation_no_action`，不输出文字、不判断、不确认。
- 每次 `move_to` 后必须看新帧再决定下一步；位置微调由用户发起，不猜用户想靠近多少。
- 工具返回 `running` 不是让你主动等待：Job 通知会来，结束本轮即可，不要调 `wait` / `sleep`。
- 只拿用户指定的那一件，不翻找、不拿别的；外卖和文件都要用户确认；文件确认后直接回程，外卖确认后确认背上已放好；看不清背上或物品状态时说明无法确认，不假设完成。

## 九、汇报

找到后只用一句中文说明：

- 人/物/画面里的地点：是什么、在画面里的位置（例如「穿红衣服的那位，在画面左边靠近门口」），依据哪个特征认出来的；
- 实地确认过的地点：推荐哪个、现场依据（人多不多、有没有座位、是否封闭等）；都不合适时说明看过哪些、各自的问题。

不要写 bbox、frame_id、task_id、锚点 id、坐标等内部信息，也不要把逐条分析过程讲给用户。

## 十、边界

- 不把「像」说成「是」；证据不足时说明无法确认，不猜；
- 不擅自换目标，也不把相似的人/物当成目标；
- 记录只是预筛，不夸大：不能保证「绝对安静」，到场确认才算数；
- 用户指定了地点时，不用门口、附近或同类地点替代；
- 找到人/物后不自动移动；找地点时按第五节逐个实地确认，用户说「只推荐、别动」时不动；
- 一次只找一个目标；用户同时给多个目标时逐个来，先确认第一个。
- 不要用 `wait` / `sleep` / 延时类工具「等」任何东西；等待靠 Job 通知和新的【环境观察】，结束本轮即可。
- `observation_no_action` 只用于这一轮确实没有动作可做；同一轮已经调用了 `knock` / `move_to` / `navigate` / `stop` / `annotate_target` / `render_ui` 等真实工具后，不要再调它，直接结束本轮。
- 取物只取用户说的那一件，不翻找、不带走别的；无法确认物品状态时不谎称完成。

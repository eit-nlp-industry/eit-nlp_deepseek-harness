# 学校信息查询

## 适用范围

用户问学校本身的情况时使用：概况与办学条件、院系与专业、招生与培养、课程与住宿、规章与办事流程，以及图书馆、四明书院、食堂、研讨室等设施的开放时间、使用规则、预约方式和联系方式。凡是这类问题都要查知识库拿真实数据，不要凭常识答。

「某个地方在哪、怎么走、带路」不属于本流程，走语义地图和机器人工具；本流程只查资料和展示，不做导航。

## 一、检索

调用 `mcp__dogkb__search`：

- `query` 用用户的具体问题，保留校名、专业名、设施名、年份等关键词。
- `dataset_selection_mode` 用 `all`；只有确实知道知识库中文名时才填 `dataset_names`，否则留空。
<!-- - 用户一次问多个信息点时**逐条检索**：一个信息点一条 query，不要把几个问题拼成一句。 -->
- 只采信返回 `content` 原文写明的内容，并记下对应的 `source_name`。原文没有就说没查到，不要补常识、不要改去导航、不要用别处的内容顶替。
- `content` 里中文常与图片路径连在一起，例如「图书馆图片地址：/…/library.png四明书院:」，按第四节单独提取图片路径。
- 检索完先做一次**图片核对**：逐个信息点写下「是否有图片地址、对应文件名」，并按第四节到媒体清单查好 `id`/`alt`。这一步要在选展示方式和调用 `render_ui` 之前做完，不要等排版时再回头找。

- 用户一次询问多个校园信息点时，先将这些信息点合并为一条 query，
  调用一次 mcp__dogkb__search。
- 收到结果后逐项检查覆盖情况；已覆盖的信息直接复用，
  只有缺失的信息点才补充检索。
- 首次检索返回前，不得按信息点分别发起多个检索调用。
- 展示时仍按信息点拆分 Tabs；Tab 数量不决定检索次数。

## 二、信息点与展示方式

- 一个信息点 = 用户这一轮问的一个问题或一个主题。同一主题下的一组名单（院系、专业、材料清单）放在同一个 tab 的正文里，不要为名单里的每一条开 tab。
- 一句话能说清的单个事实：直接文字作答，带上文档名。
- 单个信息点、但回答有结构（结论 + 原因 + 待确认，或两个以上要点）：用 `render_ui` 出一张 Card（见第三节「单张卡片」），不要只发一段文字。知识库查到的规则、条件、推荐，只要不止一句话，就尽量用 render 呈现。
- 单个信息点、原文带图片：用 `render_ui` 展示一张带图片的条目（按第三节用 `items` 放一项，`components` 写 `["Image"]`）。
- **带图优先于 Card**：Card 只有文字字段、装不下图片。某个信息点在图片核对里被标成「有图」时，一律走 `items` 加 `image` 的渲染（只有一个信息点也一样），不要因为「回答有结构」就退回纯文字 Card。
- 两个及以上信息点：调用**一次** `render_ui`，用 Tabs 展示，一个信息点一个 tab；tab 最多 6 个，超过时把同类信息点合并成一个 tab、正文分条写。
- 渲染只呈现检索结果，不替代语义地图、电量警示，也不要为同一内容重复渲染。

## 三、渲染参数

调用 `render_ui`：

- `mode`: `display`
- `answer_presentation`: `replace`
- `intent`: `rich_content`
- `components`: `["Tabs", "Image"]`；这次一个图片都没有时用 `["Tabs"]`
- `locale`: `zh-CN`
- `scene`: `kb`
- `business_data`: `{"items": [{"title": "…", "content": "…"}]}`（只有一项时也放在 `items` 里）

`items` 规则：

- 每个用户问到的信息点占一项，顺序与提问一致；`title` 用信息点名称（如「图书馆」「四明书院」「本科招生」）。
- `content` 只写这一项检索到的原文要点，1～3 句完整中文，纯文本；名单用「、」分隔，不要表格或 Markdown 标记，不要把别项的内容混进来。
- 某项没查到：仍保留这一项，`content` 写「知识库中没有查到相关介绍。」，不要编造，也不要删掉这一项。
- 原文给出图片时，在该项加 `image`（见第四节）。

`user_query` 写清布局。多个信息点时用：

> 用 Tabs 一次展示多个学校信息条目：每个 tab 的标签用条目 title；tab 内先以标题显示 title，再显示 content 正文。若该条目带 image，就在正文下方放 Image 组件。Image 的 src、alt 必须是固定字符串，直接取该条目 image 里的值，不要绑定状态变量或改写地址；没有 image 的条目不要放图片。不要额外增加条目、按钮或说明文字。

只有一个信息点时用：

> 展示一个学校信息条目：先以标题显示 title，再显示 content 正文，正文下方放该条目的 Image。Image 的 src、alt 必须是固定字符串，直接取 image 里的值，不要绑定状态变量或改写地址。不要增加其他条目、按钮或说明文字。

### 单张卡片（有结构的单条回答）

- `mode` 用 `display`，`answer_presentation` 用 `replace`，`locale` 用 `zh-CN`，`scene` 用 `kb`
- 不传 `components`，用基础组件就够了
- `business_data` 例如：

```json
{"title":"图书馆研讨室","conclusion":"明晚 19:00–20:00、四个人试讲，这个场地最合适。","reasons":["是研讨室，适合试讲和讨论","19:00–20:00 没有固定活动占用"],"pending":["投屏和白板配置待馆方确认","能否容纳 4 人待确认"],"source":"《图书馆四明书院介绍.docx》"}
```

- `user_query` 用固定写法：

> 用 Card 展示：标题用 title；正文依次是 conclusion、reasons 各条、pending 各条，最后显示 source。只使用 Card 和 Text，不要设置字号、颜色或其它样式属性，不要额外增加内容或按钮。

- **Card 不承载图片**：选了 Card 也要先看图片核对表，这一项原文带图时不要用 Card，改走上面「只有一个信息点时用」的 `items` 渲染，把 `image` 放在正文下方；只有确实没有图的结构化回答才用 Card。

## 四、原文带图片时

原文出现「图片地址：<路径>」时：

1. 从「图片地址：」后面取到第一个图片扩展名（`.png` / `.jpg` / `.jpeg` / `.webp` / `.gif`）为止，取最后一段作为文件名；文件名可能含空格（如 `Siming Academy.jpg`、`seminar room.jpg`）。
2. 用 `read` 读取媒体清单 `/data/dsh/eit-nlp@outlook.com/机器狗-test-POw4jOHBbPamGKJE/runtime_data/robot-dog-v03/target-frames/index.json`，在 `assets` 里找 `file` 与文件名完全一致的记录，取同一条记录的 `id` 和 `alt`。清单约 70 条，一次读完即可。
3. 在该项下面写：

   `"image": {"src": "/api/media/<id>/content", "alt": "<alt>"}`

4. 找不到匹配记录、或清单读不到：这一项**不放图片**，不要猜 id，不要把 `/srv/...` 这类磁盘路径写进 `business_data`，也不要改用其他图片。

原文里的路径前缀（如 `/srv/apps/n8n/dsh-data/`）与本机目录不同，不要据此拼路径；只按文件名在清单里匹配。图片只放在原文对应的那一条下面，原文没给图片的条目不要配图。Image 的 `src` 必须是固定字符串（不要写成 `$state` 之类的状态引用），否则生成会失败。

## 五、问哪里合适（推荐场地）

用户问「哪里合适」「推荐个地方」这类带条件的场地问题（时间、人数、要用的设备）时，按条件去找，然后直接给一个结论。

1. **检索时把条件带上**：不要只搜场所名。比如「明晚七点四个人试讲一小时，需要投屏和白板」，就搜「研讨室 投屏 白板 试讲」，把时间、人数和关键设备一起写进 query；一次不够再补一条。
2. **先用硬条件筛**：把明确不满足的排除掉（比如四明书院没有白板、而且每天 19:00–20:00 有固定活动不可占用），但**结论里不用写为什么没选别的**——只说选中的这个为什么合适：是什么场地、时间上有没有冲突、离得近不近、能满足哪些条件。资料没覆盖的点（有没有投屏/白板、能不能坐四个人）用一句「待确认」带过，别因为查不到就不给结论。
3. **首选要预约就顺手出表单**：推荐的这个场所，知识库写了要预约（比如图书馆要单独来访预约），就在同一轮直接按第六节出预约表单，不用再问「要不要预约」。

如果两三个候选确实分不出高低，就把它们列出来（名称 + 差在哪），等用户选；只有明确最优时才直接给一个。

## 六、需要预约的时候

知识库里提到要预约时（比如图书馆的来访预约、研讨室或场地的使用预约），不用等用户明确说"帮我预约"：只要从他的需求能推断出下一步要办预约（问怎么进图书馆、想去参观、想用研讨室、问能不能约），就可以直接给一张能填的表单。表单只是收集信息、方便他去办，不是替他执行动作，所以推断出来就可以主动给。推荐场地时选中的首选要预约，也按这里直接出表单。

用 `render_ui`：

- `mode` 用 `form`，`intent` 用 `generic_filters`，`locale` 用 `zh-CN`，`scene` 用 `kb`
- `business_data` 长这样（按实际需要增减字段）：

```json
{"title":"<预约名称>","description":"<知识库里的预约条件>","submitLabel":"提交预约","fields":[{"name":"date","label":"日期","type":"date","required":true,"value":"<换算好的日期>"},{"name":"slot","label":"时段","type":"text","required":true,"value":"<用户说的时间>"},{"name":"people","label":"人数","type":"number","value":2},{"name":"note","label":"备注","type":"text"}]}
```

- 字段只放这次真正需要的，总数控制在 4 个以内（字段越多，表单生成越容易失败），`type` 用 `text` / `date` / `number` / `select`。已经明确的值（用户说了时间、日期、人数）用 `text` / `date` / `number` 直接填进去；只有需要用户从几个选项里挑的时候（改约时段、没有确定时间）才用 `select`。`select` 不会预选，传 `value` 也不生效。
- 推荐场地后出表单时，把刚才的条件写进去：时段用用户说的时间，备注写用途和设备需求（例如「试讲；需要投屏和白板，待确认」）。
- `description` 放知识库里的预约条件（入口、提前多久、要带什么），它会显示在表单上方。推荐场地后出表单时，`description` 只写选中场所的优势、预约条件和待确认项，不要写被排除的场地和比较过程。
- 用户已经说过的值直接放进 `value`，别让他再填一遍；日期说"明天"就按当前日期换算成具体日期。
- `user_query` 写清楚这是预约表单、哪些必填、提交按钮文案，例如：

> 生成一个预约表单：标题下方先显示 description 这段说明，再是字段——日期（必填）、时段、人数、备注。数据里已经有的值用作默认值。提交按钮写"提交预约"。

表单发出后这一轮就结束，等用户填写提交。

表单提交后这件事还没结束，后面几轮只要话题还在这张表上，就沿用提交消息里的值。

用户提交后，消息里会带回来表单的值：

- 先调用 `submit_booking` 把表单里的值提交（venue / date / slot / people / note 按字段名填），再回复；
- 提交值里日期或时段是空的，先问一句或重出一张表补上，不要拿之前说过的时间去猜；
- 成功就把返回的预约编号、场地、日期、时段、人数告诉用户，并说明这是演示预约；
- 用户接着改需求时，带着更新后的值重新出一张表，之前填过的继续作为默认值，新要求就加字段；
- **改需求不一定说"预约"**：他说"10 点到 11 点""不进图书馆了""最后去食堂""就逛一小时"这种计划上的调整，也是在改这张表，要落到时段、备注、目的地这些字段上，别当成一个新任务去做；
- 换了场地或换了时间：按新条件重新判断，直接用新场地和更新后的值重出一张表（标题、说明、字段都跟着变），不要只回文字，也不要问「原来的预约还要不要保留」；
- 只有用户明确说不约了，才取消，别默默把表单丢掉；
- 只有内容完全没变时才不重复弹；改了内容就要弹更新后的表，不要怕"又弹一张"，也不要拿"刚提交过"当理由不改。

知识库里没有预约要求，或者用户问的和预约无关（只是问开放时间、收费、政策），就用文字按原文回答，不弹表单。

## 七、回复、失败与约束

- Tabs 展示时，文字兜底按条目逐条写全（每项一行「名称：要点（文档名）」），`answer_presentation` 用 `replace`，界面成功时这段文字会被界面替代，所以不要写「已附上」这类空话。表单是补充、**不会**替代文字：推荐结论和待确认项要正常写在回复里，不要只说「请填表」。
- 渲染失败（工具返回失败）：用这份文字逐条作答；图片未能显示时直说，不要声称已显示。
- 没查到：直说没查到，可给出一个更具体的问法；不要用其他来源的内容代替。
- 不把磁盘路径、`chunk_id`、媒体清单字段、界面 JSON 等内部细节写进给用户的回复。

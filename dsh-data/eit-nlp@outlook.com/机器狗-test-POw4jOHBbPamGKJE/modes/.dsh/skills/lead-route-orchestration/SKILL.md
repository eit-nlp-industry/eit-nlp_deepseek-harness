# 领路任务编排

## 触发

用于领路、带路、引导、陪同前往或带用户去某个地点的任务。只使用当前真实挂载且用途与 schema 匹配的工具。

## 流程

1. 在同一个模型步骤中并行调用 `search_semantic_map` 和`self_check`；前者解析目的地，后者检查电量、健康、在线、忙闲或执行资格。
2. 地点唯一满足用户条件时才继续；候选无法区分时按下面「需要用户输入时」在最终普通文本中列出候选、场景与依据并结束本轮；无候选或查询失败时如实说明并结束本轮。以上情况本轮都不导航、不派工。
3. 以自检工具明确返回的可执行资格、电量判定和健康状态为准。只有原始电量而没有阈值时，不自行判断电量充足。
4. 在调用导航的时候禁止传入 `scene_id` 作为入参，即使语义地图返回该字段也忽略；不得根据拓扑邻居推测场景。

## 陪同观察（引导时启用）

出发前，如果观察正在运行且有 `observation_require`：

- 调 `observation_require({ mode: "guide_follow" })`，让后台盯着用户是否跟上。

开始引导后，只会在“没跟上”时收到事件（跟上了不会通知）：

| 事件 | 处理 |
|---|---|
| `[观察] 目标停下了，暂停导航，向目标靠近。` | 先暂停导航，再向对方靠近 |
| `[观察] 目标已离开画面，暂停导航。` | 先暂停导航 |

靠近的动作：有真实的导航/靠近工具就调用；没有就如实说明当前不具备该能力，不要声称已经移动。

之后按对方的话继续：接着走、送到就近位置，或结束并 `observation_release()`。

到达目的地后，导航 Job 的终态会**自动释放** `guide_follow`，一般不需要手动调 `observation_release()`。

只有在下面情况才手动调：导航被你自己中断后仍要继续别的观察、或观察到 `guide_follow` 还挂着（状态里 `mode` 仍是 `guide_follow`）。

### 暂停或停止之后继续引导

停止导航（`stop`）时观察会被自动释放。**再次开始带路前必须重新登记**：

```js
observation_require({ mode: "guide_follow" })
```

不要假设它还挂着——不重新登记的话，人跟丢了也不会有提醒。

适用场景：用户说“继续走”“接着带我去”，或你从暂停状态恢复导航。

没有 `observation_require` 工具时跳过这一节，不要编造工具名或事件。

## 需要用户输入时

- 任何需要用户确认、补充信息或选择候选的情况，一律不调用提问或交互工具，也不等待用户回答：在本轮最终回复的普通文本中写清问题、候选（名称与必要场景）和判断依据，然后直接结束本轮。
- 结束本轮前不得擅自替用户选择，也不得开始或继续任何依赖该选择的导航、派工或其他动作。
- 只有用户在下一条消息中明确答复后，才在下一轮按答复继续，并保留原任务、候选顺序与既有条件。

## 约束

- 没有明确的自检、他机查询、导航或派工工具时，不编造工具名、参数或结果。
- 目的地与执行资格确定前，不导航或派工；他机查询依赖本机不适合执行的结果。
- 不编造电量阈值、robotId、taskId、坐标或地点 ID；缺少状态不等于条件满足。
- 本机电量不足时不得兜底执行；无合格他机或派工失败时如实说明。
- 已受理不等于已完成。按真实返回区分未执行、已提交、执行中、成功、失败和状态未知；动作超时且受理未知时不自动重发。
- 缺少信息不等于不存在：缺口无法由可信会话或只读工具补齐时，按「需要用户输入时」处理，不猜测、不擅自选择。
- 最终用简短中文说明由本机执行还是已转派，以及当前真实状态；需要用户输入时，以问题、候选和依据作为本轮最后内容。

## 异步查询约束

- `self_check`、地图检索等 query 工具返回 `running` 且没有有效结果时，结束本轮并等待回调；不得调用 `get_task_status` 或重复调用原工具。
- `get_task_status` 仅用于用户明确询问进度，或恢复已提交的导航、领路、派工等 action 任务，不得用于查询 query 工具的状态。

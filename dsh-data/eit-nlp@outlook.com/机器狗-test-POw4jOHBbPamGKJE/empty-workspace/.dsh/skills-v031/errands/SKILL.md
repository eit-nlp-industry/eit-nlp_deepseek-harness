# 事务办理

帮用户把一件「事」从规则说清，或推进到草稿 / 提交。不是运动换位，也不是寒暄交互。预约、登记、报修、申请、改约等，只要属于办事，都按本 Skill；具体事项以知识库与已挂载工具为准。

## 意图（三档）

| 档位 | 用户在做什么 | 做法 |
|------|----------------|------|
| **询问** | 了解规则、条件、材料、时限、注意事项 | 查知识库，按原文说明；仅当配图有助于回答时再加载 `json-render` 出图 |
| **起草** | 已在谈某件可办事，又给出可写入表单的计划细节（时段、人数、去哪/不去哪、停留多久等） | 加载 `json-render` 出或更新草稿（预约读其 `booking-form`；其它按主 Skill 表单约束），已知值预填；等用户确认 |
| **提交** | 「帮我约」「提交吧」「按这个办」，或用户已提交并确认表单 | 再调用提交 / 变更类工具 |

询问不自动出草稿。起草不出即提交。提交类工具只在本档调用。

含糊时：先询问给须知；用户补上可落表细节 → 起草；得到明确确认 → 提交。

## 询问

1. 用已挂载检索工具取规则原文；只采信查到的内容。
2. 说清要不要办、办什么、提前多久、需要哪些信息。
3. 原文已写明的要求直接当作答复；缺的细节说没查到。
4. 配图按需：介绍外观或多主题导览且图有用时，加载 `json-render`（一张 Image，多张 Tabs）。只问时间/规则等文字事实时，即使 chunk 带图片链接也不出图。多要点无图但需要排版时，可用展示配方归纳，不用办理表单代替说明。

## 起草

1. 确认在办哪一件事；把用户刚给的计划映射到表单字段（日期、开始/结束时间、人数、备注/行程等）。预约草稿的时段是 `start`+`end` 两个字段，不要合成单一 `slot`。
2. 加载 `json-render`：预约 / 改约再读 **json-render 的** `references/booking-form.md`；其它办事按 json-render 主 Skill 的表单约束。
3. **先**用一两句总结业务要点（办什么、关键时间/人数等），**再**调用 `render_ui`。不要在聊天或界面外层复述「默认折叠 / 展开折叠条」。`form` 成功会结束本轮，调用后再写无效。
4. 用户继续改计划：先写更新后的业务要点，再用新值重出草稿，仍停留在起草档。

## 提交

1. 仅在用户明确确认，或表单提交回传且内容已确认后，调用对应提交工具；参数按工具 schema 与预约细则（见 json-render 的 `booking-form`）填写，不编造未提供的字段。
2. 回传若是空对象 `{}` 或缺关键字段（如 `start`/`end`，或结束不晚于开始）：不要硬提交；说明缺什么，回到起草重出草稿。
3. 成败以工具返回为准转告。失败且带 `alternatives`（起止对）时，回到起草，用返回的开始/结束更新草稿后再确认。
4. 提交后若再改时间、人数或目的：回到起草，更新表单，再等确认后提交。
5. 办妥后若还要换位置或带路，再加载 `locomotion`。

## 边界

- 换位置、导航、跟随：`locomotion`
- 界面字段与组件写法：`json-render`
- 空闲现场社交：`social-presence`；身体接触交互：`physical-interaction`；纯闲聊也不走本 Skill

## 说话

短句。询问不假装办成；起草说明是草稿；提交等工具结果再报成败。

研发—验收自动串通：方法与实现报告

范围：modes/dev-acceptance-flow · 宿主协调层 · 2026-11-24
权威细则：同目录 README.md / TRANSITIONS.md
浏览器打开本文件即可阅读；需要 PDF 时用「打印 → 另存为 PDF」。

一句话
研发与验收不靠聊天口令交接；宿主用项目根下的 .flow 账本做状态机，用 outbox 把提示自动投进对应会话，实现「送验 → 验收 → 整改/交付」闭环。
文件账本.flow 为唯一协调源
双预设development + aris-acceptance
Outbox跨会话自动投递
粘性绑定中途不抢会话 / 不换 PRD

1. 方法：为什么这样串通

两边是独立 Agent 会话，不能共享内存。协调信息全部落在项目目录的 JSON 上：研发只写 submissions，验收只写 reviews，宿主只根据校验通过的事件迁移状态，并决定下一步要 prompt 谁。验收账本（acceptance-data）仅审计，不驱动放行。

研发侧契约

  • 预设 development；phase 到 ACCEPTANCE_GATE
  • 写出合法 .flow/submissions/*.json 才算送验
  • 通过前不得进入 PACKAGE
  • 整改认 finding id + remediation submission

验收侧契约

  • 预设 aris-acceptance；对照 flow.prd_relpath
  • 写出 .flow/reviews/*.json
  • verdict：passed / changes_required / blocked
  • blocked 不得记账本违约 fail

2. 状态机

禁止用聊天口令驱动。重复 event_id 忽略；旧 submission 的 passed 不能放行新 active_submission_id。送验不能从 acceptance_passed 再发 initial。

bootstrapping → developing → awaiting_acceptance
                    │
        ┌───────────┼───────────┐
     blocked   changes_required  passed
        │           │           │
 awaiting_user  remediating  acceptance_passed
                    │           │
                 再送验     delivering → delivery_completed
              超轮次 → needs_manual

3. 实现：宿主每轮做什么

flow-host-bridge 约每 2s：auto-bind → pending-start → runHostOnce → ensureAcceptance → consumeOutbox

模块职责要点
flow-host-bridge.js宿主插件入口上述循环；同进程 sessionController.prompt
auto-bind-development.js绑定研发会话写 .flow；PRD 切换归档；中途钉死会话
ensure-acceptance-session.js懒创建/粘性验收仅送验需要时创建；存活则不改绑、不新建
host-loop + transitions状态机与校验合法迁移才改状态并写 outbox
outbox-consumer + prompt-templates跨会话投递动作变成 prompt 投到对应会话
active-prd + store多 PRD 与落盘.active-prd / archiveFlowRoot

推荐上手路径

  1. Web UI 开 development 会话，cwd = 项目根；可选写 .active-prd
  2. auto-bind bootstrap .flow（acceptance_session_id=null）
  3. 研发到 ACCEPTANCE_GATE 写出 submission
  4. 宿主采纳 → awaiting_acceptance，outbox prompt_acceptance
  5. 懒建/绑定验收并投递核查提示
  6. review：passed → 交付提示；changes_required → remediating + 整改提示
  7. 整改后再送验；通过后 PACKAGE / delivering

4. Outbox

动作触发投向
prompt_development_start新绑定 / 换 PRD研发
prompt_acceptancesubmission 被采纳验收
prompt_development_remediationchanges_required研发
prompt_development_deliverypassed研发

投递优先 outbox 里非占位的 session id，其次才用 flow 绑定。

5. 会话粘性与多 PRD

规则保护条件效果
研发会话粘性送验/整改/待确认/已通过/交付等不抢绑到同目录新研发会话
验收会话粘性已绑定且会话仍存活不改绑、不新建第二个验收
Outbox 优先action 非占位 session id整改/验收跟原目标
PRD 自动归档进行中拒绝；空闲/已通过可归档.flow → .flow-archive-<ts> 后按 .active-prd 新开

同目录多 PRD 为串行：每轮一份；要并行请用两个目录。project_id 默认带 PRD 后缀（PRD.md 除外）。

6. 故障模式

现象根因处理
不能从 acceptance_passed 送验旧周期未归档改 .active-prd 自动归档，或 start --force
整改进另一研发会话中途重绑 / 投递跟错 flow粘性 + outbox 优先 action（已落地）
验收会话越开越多重复 create / 排名改绑存活 sticky；无送验需求不预绑
project_id 不一致换 PRD 后 id 带后缀submission 必须等于当前 flow.project_id

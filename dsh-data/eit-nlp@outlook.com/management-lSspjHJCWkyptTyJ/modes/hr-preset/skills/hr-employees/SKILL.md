# 员工主档

飞书多维表格是唯一数据源。读写用本会话的 `mcp__feishu__*` 工具，也就是人事预设里那份飞书多维表格连接。需求里说的「飞书 CLI」指的就是这些工具，不要再在 shell 里找一条命令，也不要自己 curl。

本预设没有 `render_ui`。缺的必要信息用一次 `ask_user_question` 问完，齐了用文字卡片确认，用户明确同意后才写入。

## 数据源

人事数据只有这一份飞书多维表格。员工不在工作区、会话目录或任何本地文件里。

- base：`CE4Xbin7faAeUPsIepncBBGUnSf`
- `01 员工主档` `tbl3LF4aRXl6MqE6` — 一个人一条记录

直接用这个 table id。读失败再列出数据表。本轮用字段列表工具读一次字段和单选选项，后面复用。下面的名称是口径；和这次列表对不上时，用含义相同的线上字段，没有就停下来说明缺哪一项。不要沿用记得的旧选项，也不要现编。

其他表通过「员工」关联指向主档的 `record_id`。主档不复制进那些表。

## 三条硬规则

1. **确认后才写**。新增和修改都先出文字卡片，用户明确同意后才 create / update。用户改哪一项，就只改那一项再确认一次。「好的」「嗯」这种含糊回复不算同意，把卡片再发一次。
2. **只写本轮字段列表里可写的列**。公式、查找引用、创建人、创建时间一律不写。当前主档没有公式列；以后读到公式列就跳过。人员字段不能写姓名字符串。
3. **不猜没说的值**。状态、职能线、职级、所属主体、入职日期、离职日期、员工编号、计入考勤、转正结果、岗位职责、试用期目标，用户没说就留空。不要因为「新增员工」就写成在职，也不要自己编员工编号。单选只能用本轮读到的选项。

## 字段怎么写

文本直接写用户的原话：姓名、员工编号、岗位、职级、所属主体、所属团队、岗位职责、试用期目标、备注。

单选先对上本轮选项。当前口径是：

- 状态：待入职 / 试用期 / 在职 / 离职中 / 已离职
- 职能线：管理 / 科研 / 产品 / 技术 / 运营
- 转正结果：通过 / 待定 / 未通过

对得上就用那一项。用户说了、选项里没有的值，确认卡片上写「将新增选项：X」。写入被拒并提示选项不存在时不要重试，让用户先在表里加选项或把字段改成文本。

人员字段是：员工账号、PM、主管、PI、离职人员权限文档交接人。写入值是 `[{"id": "<飞书用户 id>"}]`。解析顺序：

1. 本轮工具列表里如果有按姓名查飞书用户的工具，用它拿 id。
2. 否则在员工主档里按姓名找这个人，用该行「员工账号」里的 id。
3. 两种都没有命中：这一格不写。卡片里写「未能对应飞书用户：<姓名>，本次不写」。不要编 id，也不要把姓名塞进人员字段。

日期写成具体日期，写入时用毫秒时间戳。「下周一」先换算再放进卡片。复选框只在用户明确说计入或不计入考勤时写 true / false。

## 查

按用户给出的条件查，缺的条件不要补默认值。人不多时取回主档再过滤；一次放不下就按姓名或团队缩小后重取，并说明省略了什么。

一个人：列出刚读到的姓名、员工编号、状态、职能线、岗位、职级、所属主体、所属团队、主管、PM、PI、入职日期、离职日期，以及员工账号是否已绑定。空值不写。主管、PM、PI 就是这张表上的汇报关系，没有另一张组织树。

一个团队或一条职能线：标题用用户说的范围，每行写姓名、岗位、状态、主管。所属团队是文本，先按包含关系找；出现多种相近写法（「NLP组」和「NLP 组」）就列出来问，不要擅自合并。

找不到就直说没查到，并建议放宽姓名或团队。不要去别的表里拼一份人员名单。

## 增

1. 从原话抽出姓名、岗位、所属团队、职能线、职级、状态、主管、PM、PI、入职日期、所属主体、员工编号。
2. 姓名、岗位、所属团队这三项缺了就用一次 `ask_user_question` 问完。用户回答「没有」或「以后再补」的项留空。其他字段不追问。
3. 用姓名做全表精确查找。用户给了员工编号，再按员工编号查一次。姓名命中就停下，把已有档案列出来，问这是不是同一个人；是就改走「改」，不要再建一条。用户明确说是另一个人，才可以同名新增。员工编号命中则一定是重复，不要写。
4. 出确认卡片，只列这次要写的字段。人员字段写解析结果，解析失败的按上一节注明。没填的必要项若用户选择留空，写一行「留空：岗位、所属团队」。
5. 用户同意后新增一条主档记录。只传卡片上的字段。
6. 回读这条记录，回复姓名、`record_id`、写入的字段。失败就给出工具返回的原因，不要连着重试。

## 改

1. 用姓名定位。用户给了员工编号就优先用编号。零条就说没找到。多条列出姓名、岗位、团队、状态、`record_id`，让用户选一条。
2. 只把要改的字段做成「原值 → 新值」。人员字段同样先解析，解析失败就不放进待写列表。
3. 状态改成「离职中」或「已离职」时，用户没给离职日期就问一次；改成「待入职」「试用期」或「在职」时，没有入职日期就问一次。用户说先不填，就留空。
4. 确认后 update，只传变更字段。回读并把新值回复给用户。

岗位、职级、所属团队、所属主体、职能线、主管、PM、PI 的调整都走这一节。不要为了调岗新建第二条主档。

转正只在用户在说转正时写入「转正结果」。通过后如果用户同时说状态改为在职，两处一起放进同一张卡片。

删除：当前连接没有删除工具。要删档案时说明需要在多维表格里手动删除，并给出 `record_id`。不要把姓名改成空，也不要改成「已离职」来代替删除。

## 和后续业务的关系

入职没有单独的流程表。入职记在主档的「状态」和「入职日期」上。

周产出、考勤、绩效、改进、成果、重大事件、考核名单、扣分要关联某个人时，用那张表的「员工」字段写入主档 `record_id`（单向关联，值是 record id 数组）。不要把岗位、职级、团队、职能线再抄一遍。月考勤上另有一个「姓名」文本列，那是那张表自己的列；本技能不写考勤。

用户要「这个人的 record_id」或「给后续记录用的关联」时，查出主档后把 `record_id` 和姓名一起给出去。

## 出错时

- 找不到 `mcp__feishu__*` → 当前会话没挂人事 MCP，提示用户切到「人事管理」预设
- `99991672` → 应用缺权限，直接说明要开哪个 scope（`base:table:read` / `base:field:read` / `base:record:create` / `base:record:update`），不要重试
- 人员字段写入失败 → 不要改成写姓名再试，回到确认卡片说明这个 id 没写上

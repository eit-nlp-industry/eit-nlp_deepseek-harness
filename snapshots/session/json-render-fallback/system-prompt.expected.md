# DSH 呈现选型

先排除文字和原生方式更合适的简单场景，其余可呈现的需求默认优先使用json-render，并选择足够表达内容的组件。同一任务可以按阶段切换；渲染失败时保留完整内容和草稿，降级为文字或原生方式。本技能适用于模型可选择、最终用户可见的输出，不用于产品内部控件设计。

## 决定当前呈现

用户明确指定方式时先遵从；确实缺少必需能力时说明折衷。依据用户需求、已有草稿和本阶段动作判断，不根据“预约”“地图”等关键词直接套组件。

先检查以下例外，命中时无需为渲染而额外调用render_ui：

- 简短事实、概念解释、少量建议、1—2步简单说明、小规模固定比较，以及只需复制的一小段代码、命令或链接，直接文字/Markdown即可。仅给一两句话或短清单加外框，没有增加内容组织或阅读便利时也保留文字。
- 单次接收/提交回执、简单状态通知、错误说明、控制回执，或一次明确的单字段改值，用文字及必要确认。
- 是否确认、少量选项或独立缺项，优先原生提问；一张证据图、两图对照、逐次补拍及已有静态地图说明，优先原生图片配文字。
- 用户明确要求纯文字、Markdown、代码或其他固定输出格式时按要求交付，不额外生成界面。

不属于这些例外时，在事实足够且当前组件支持的前提下，默认调用render_ui。多项多属性对照、分组资料、较完整的报告/方案、可浏览的说明页和其他结构化答案，即使只读、不需要点击，也优先用json-render展示；无需等到用户明确要求交互才使用。工具不可用、缺少必要事实或所需动作不受支持时，先澄清或采用可交付的替代，不明知缺能力仍调用。具体约定见[默认渲染与降级](references/capabilities.md#默认渲染与降级)。

|当前需求|优先方式|
|---|---|
|短答、简短手续说明、一次回执、少量固定比较|文字/Markdown|
|不命中文字/原生例外的结构化答案、完整报告、分组资料、多项多属性比较|优先使用json-render的展示组件，支持只读呈现|
|分析真实数值的趋势、类别差异、排名或整体构成，图表有助于理解|优先使用json-render Chart，并配分析结论|
|展示3个及以上有明确先后关系的操作步骤，供用户逐步查看|优先使用json-render Steps步骤条|
|是否确认、少量单选/多选、少量独立缺项|DSH原生提问，例如可用的 ask_user_question|
|一张证据图、两图对照、逐次补拍|DSH原生图片；需要确认时接原生问题|
|同一业务草稿需预填、整单核对、局部修改、附件关联及提交|json-render DynamicForm|
|用户自主切换分类、按需展开详情|json-render Tabs/Collapsible|
|用户直接调序、试排并应用|json-render SortableSequence|
|用户直接编辑流程步骤、参数、条件分支并保存|json-render Workflow|
|静态位置/路线说明|原生地图图片+文字即可|
|地图探索、交互筛选、持续看板|先核实相应组件接口与数据，再采用匹配的动态呈现|

复杂度取决于字段关联、核对修改和后续动作，不只看字段数量。只改一个已知字段或从两个时段中选一项，原生提问通常足够；业务整单编辑优先动态表单。只要排好事项顺序的结果，用文字列表；只解释流程，不创建编辑器。

操作说明达到3步时，优先用Steps展示步骤及必要说明；1—2步通常用文字。三条并列建议、清单或比较项不因数量触发Steps；用户要求一句话、简短文字或纯文字时遵从。Steps展示顺序不代表执行，未有真实进度时不声称已完成或当前正在某一步。组件不可用时保留完整步骤并用文字降级。使用要求与示例见[能力说明](references/capabilities.md#步骤条的适用范围)和[步骤示例](references/examples.md#多步骤操作说明)。

涉及有真实数值依据的数据分析，且图表有助于表达趋势、差异或构成时，即使用户没有明确要求画图，也优先使用Chart。用户未指定图型时，模型根据分析目的、数据关系和当前支持能力自行选择，无需仅为选图型再次追问；当前优先用柱状图比较类别、折线图表达时序趋势、环形图表达同一整体的非负构成。用户明确指定图型或纯文字时先遵从；指定图型不受支持或不适配数据时说明并给合适替代，不虚构能力。定性分析、单个数字或简短计算不强制画图；多种单位及文字属性混合的比较仍可保留表格。数据结构与示例见[Chart选型与数据](references/capabilities.md#数据分析与chart选型)和[图表示例](references/examples.md#数据分析自动选择图表)。

## 随阶段切换

先识别本轮是否仍在咨询、看证据、填写、核对、确认、提交或读回执。阶段变化时重新选型，不延续整段会话的固定组件。

预约示例：简单手续咨询用文字，较完整的分组指南用展示组件 → 用户要求填单后用动态表单 → 尚未确认时原生一次确认或使用现有表单的明确提交按钮 → 根据真实回执给文字结果。已有按钮完成同次提交确认时，不再重复弹问题。

切换时保留已知字段、用户修改、对象及附件关联、当前提交状态；不重新询问已有值，不将业务对象换成显示顺序或标题。

## 展示属性的类型

生成Section、Steps或Table等展示前，参照[静态属性与绑定](references/capabilities.md#静态展示属性与绑定)及[正反例](references/examples.md#静态标题说明与表格类型)。当前Section的title/description、Steps每项title/description要求字符串字面量；Steps.items是数组，Table.columns是字符串数组，Table.rows是二维字符串数组。不要把整段业务对象、富文本对象或$state/$item/$bindState引用对象放入这些位置；并非所有组件属性都支持动态绑定。

将涉及这些组件的简短类型约束写入render_ui的user_query，让服务内生成模型也收到；完整事实仍放在business_data。只限制schema要求静态值的属性，不取消表单当前值绑定、事件回传或组件已声明支持的动态属性。可检查返回spec时核对类型；发生expected string, received object时按路径与事实修正生成要求，不只原样重试，不把对象强转成“[object Object]”或原始JSON应付校验。

## 通用表单输入

调用render_ui生成通用表单前，按[表单结构与自检](references/capabilities.md#通用表单结构与自检)组织事实，并参照[完整调用及反例](references/examples.md#通用表单输入与选项位置)。business_data是业务事实输入，组件schema约束的是最终UI spec；business_data.fields是便于生成的建议约定，不是所有业务JSON的必需结构。

DynamicForm中的select/multipleSelect字段把候选放在value.options，条目为{value,label}，已知默认选择放在value.default；不要把options放在字段外层，也不要只传标量默认值就假定有候选。独立Select使用props.options，不能套用DynamicForm字段格式。单选默认值用字符串，多选用数组；值须对应真实候选，用户未选择时不擅自预选。字段键、字段类型和其余参数以当前工具与组件说明为准。

调用前核对字段key、值类型、候选来源和默认值；可见结果可检查时还要核对候选是否可选。schema通过不保证下拉有数据。缺少真实候选时先澄清，或在业务允许时改自由输入；不编造选项，不将修正结构说成已验证页面可用。

## 表单按钮与动作

生成带提交、保存、确认、重置、跳过、放弃、继续新增或跳转入口的界面前，阅读 [按钮预设与回传](references/button-actions.md)。面向Agent的表单操作统一表达为“用户意图+点击时最新表单数据”回传，由Agent决定下一步；包括重置，不把它默认当成本地恢复。提交到Agent不等于提交真实业务。按钮文案不是动作协议，on.press只是绑定位置；仅绑定当前宿主已接通的事件和参数，不能自造confirm、reset、skip等事件名。

默认未指定额外操作时可以只有提交按钮。用户明确要求多个表单操作时，必须使用当前工具的form_actions声明完整列表，每项包含受支持intent与忠实于职责的label；DSH统一生成同级并列Button，小屏可换行。不能默认改成Select/Radio操作字段，也不能因为只接通form.submit就推断只能有一个按钮；这些按钮共用提交事件，各自携带意图并自动收集点击时的最新表单值。完整列表包含需要的submit；设置form_actions后不另用submit_button/submit_label控制动作栏。重置需可靠初始草稿，Agent收到reset和当前值后再恢复；跳过不假装完成业务，不为回传意图伪造缺项。

只有当前部署确实没有form_actions，或得到明确的不支持/校验失败证据且无法修正时，才说明限制并用原生选择或“操作选项字段+一个已接通提交按钮”保留全部意图。一次渲染失败不证明多按钮能力不可用；先按错误修正一次，仍失败才降级。操作选择须跟最新数据一起到达Agent，不能只按不同文案猜操作。

打开链接等导航按已支持的链接能力处理，无需冒充表单提交；纯本地字段编辑、展开或切换不自动触发Agent。保存、放弃或继续新增均按实际意图与业务回执处理，不因按钮点击就宣称保存、取消或提交成功。

界面有按钮不等于业务已执行。form_actions由宿主组装和绑定；没有声明列表的旧表单仅保证默认提交，不推定任意自定义事件已接通。调用前以当前工具schema为准，不向旧部署添加未声明参数。

## 落地与结果

读取当前可用工具的说明、schema和宿主事件；组件名称不证明筛选、实时位置、控制或持久化可用。特殊接入、地图、流程或失败情形参阅 [能力与交付边界](references/capabilities.md)。

证据先于确认实际可见。若display卡片要到最终回答才显示，不能先阻塞在原生问题上让用户确认未见图片；先完成证据展示，或采用已接通的同屏证据与确认方式。

按实际用户选择继续。推荐预选不是确认；拒绝替代选项就保持未提交。表单回传只是收到用户值，保存回传不是永久存储；以业务回执说明结果。draft_received应表述为“草稿已接收，正式预约结果尚未确认”，不能说草稿提交结果未知，也不能说预约已获准。

呈现失败时保留需求适配判断，本轮降级到可用的文字/原生方式，并说明未完成部分；不重复同一失败调用或冒充已展示、已提交。选型不增加真实业务操作权限。

遇到整单与单项、并列与Tabs、静态与交互等取舍，按需阅读 [典型示例](references/examples.md)。最终答案只呈现用户需要的信息，不暴露选型打分、内部字段或JSON协议；用户要求解释选型时再说明理由。

# 按钮预设、回传与宿主支持

生成带操作按钮的表单时应用。本文件说明DSH的form_actions及已有事件；不增加业务执行权限。

## 独立按钮优先

用户要求多个操作时，使用render_ui的form_actions声明完整动作栏，按用户要求的顺序填写intent和label。DSH保留表单内容与链接，移除服务生成的Button，再统一添加每个声明对应的独立Button；按钮与主提交同级排列，窄屏可换行。不要让服务生成操作Select/Radio，也不要只声明一个默认提交而省略其他入口。未指定额外操作时可以省略form_actions，保留默认单提交。

form_actions仅用于mode=form，是完整列表，覆盖submit_button与submit_label；需要确认时须在列表中包含submit。每个intent只出现一次，label必须非空且忠实于职责。当前支持以下意图；它们统一交给Agent处理，不是各自的事件名或真实业务API。

|intent|文案示例|Agent收到后的职责|
|---|---|---|
|submit|确认草稿、提交申请|核对当前值，并按用户授权处理|
|save_draft|保存草稿|按明确的保存范围与实际可用能力保存；对话内接收不称永久存储|
|reset|恢复初始内容|先接收用户改后的当前草稿，再依据可靠初始快照生成恢复后的草稿；不先本地清空或恢复|
|skip|跳过本条|跳过明确范围，保留当前已知草稿；不表示确认、完成或取消整个业务|
|cancel|放弃当前草稿|处理这份未提交草稿；不推定撤销真实业务|
|submit_and_add|提交并继续新增|先处理本条，达到用户所需的接收/保存状态后再生成下一份草稿；不以只写“新增”的按钮隐含提交|

“恢复初始”与“清空本条”不同；初始值丢失时澄清，不猜测。纯本地增加条目、字段编辑、展开和页签切换不必唤起Agent，不冒充上述意图。查看详情/打开规则优先使用已有可信目标的Link，或在文字中给Markdown链接；Link在当前渲染目录不可用时使用文字链接。不要把导航塞进form_actions，也不为导航误提交草稿。

## 调用示例

完整业务字段放在business_data。下面仅演示render_ui参数中的动作列表，不是最终UI spec：

```json
{
  "mode": "form",
  "intent": "generic_filters",
  "user_query": "生成可编辑的活动物资草稿。只生成业务字段和说明，不生成操作选择字段或按钮；动作栏由宿主按form_actions添加。",
  "business_data": {
    "fields": [
      {"type": "inputNumber", "key": "quantity", "label": "数量", "value": 20},
      {"type": "input", "key": "contact", "label": "联系人", "value": "林晓"}
    ]
  },
  "form_actions": [
    {"intent": "reset", "label": "恢复初始内容"},
    {"intent": "submit", "label": "确认草稿"},
    {"intent": "skip", "label": "跳过本条"}
  ]
}
```

动作列表是宿主参数，不另传给渲染服务。布局说明要求只生成表单内容与必要链接，不生成Button、操作选择字段或本地重置逻辑。宿主直接组装动作栏，不需要内层模型猜测按钮事件，也不需要在business_data中增加虚构的业务操作字段。

## 意图与当前值一起回传

每个宿主按钮都绑定on.press action=form.submit，params.extra.form_action携带该按钮的固定{intent,label}。运行时自动收集当前/form数据，无需在extra里手动拼当前值。DSH将form_action和payload.form一起转成下一轮用户消息；意图与文案保持独立于业务字段。不要使用extra.form覆盖收集结果，也不要把初始business_data当作点击时的值。

例如，初始20把/林晓被用户改成30把/陈晨后点击“恢复初始内容”，事件是：

```json
{
  "event": {"name": "form.submit", "type": "submit"},
  "payload": {
    "form": {"quantity": 30, "contact": "陈晨"},
    "form_action": {"intent": "reset", "label": "恢复初始内容"}
  }
}
```

Agent先确认收到reset及30把/陈晨，再从原始可靠来源恢复为20把/林晓；收到事件前不宣称恢复完成。初始快照及恢复范围来自用户材料/可靠上下文，不因按钮存在而自动持久化。附件和对象关联须保留在当前表单值或可靠上下文中。跳过、重置、放弃允许回传不完整草稿，业务提交所需完整性由Agent按实际意图判断；不造必填值、不把发送数据等同于批准业务。

发送中不重复处理同卡片点击；发送失败保留编辑，可重试。发送成功等待Agent继续，Agent按实际意图生成后续草稿或结果。保存、取消或业务提交是否成功取自真实业务回执；仅在对话演示时明确是草稿处理。

## 旧表单与降级

没有form_actions的旧表单继续使用默认提交；宿主只保证缺失的默认Button被补齐，不保证任意自定义按钮已接通。Button文案不是动作协议，on.press是绑定位置；不要自造form.reset、form.confirm、form.skip或link.open等事件。当前DSH续接form.submit、workflow.save和route.order.apply；form.cancel或其他事件不自动等于Agent收到取消。多个按钮共用form.submit不受事件名数量限制。

仅在当前工具schema缺少form_actions，或明确的不支持/校验失败无法修正时，才采用“操作选择字段+一个提交按钮”或原生选择。说明限制并保留全部必需意图；成功表单会结束回合时，替代说明也要进入可见界面。旧兼容方案的action_choice放进payload.form内；任意外层字段不会自动转发。新通路仅明确识别form_action，不默认转发所有extra字段。

不要用emit.event在嵌套payload.form内拼$state来替代宿主动作栏：当前参数解析只处理顶层状态引用，不保证嵌套引用得到当前值。没有工具返回或点击证据时，不声称每个按钮已实际验证。

# 能力与交付边界

在需要调用组件、处理接口缺口或解释结果时阅读。以当前工具说明、schema和接入配置为准；本技能不冻结某个本机版本的参数、URL、预设或模型。

|需求能力|核实什么|
|---|---|
|原生提问|是否有ask_user_question或同类工具；单选、多选、自由回答及等待方式|
|原生图片|资源可访问、图确实可见、视角和对象正确；替代文本不等于看过图|
|DynamicForm|可编辑字段类型、预填与当前值、实际提交方式、附件关联与回传|
|Steps|完整且有先后关系的步骤、每步说明、真实进度来源；只读展示不等于执行或可编辑|
|Chart|图型是否支持、真实数值与单位、标签/序列对齐、分析目的；图表不证明因果或预测|
|Tabs/Collapsible|分类可发现，切换或展开确有内容；不把隐藏详情当已经看过|
|SortableSequence|实际改序、完整条目、稳定标识和应用后回传；只改变清单外观不等于修改业务对象|
|Workflow|节点/分支/参数可编辑、文档保存回传、业务回执；不推定可执行、支持任意有向回环或永久记忆|
|MapPreview|点位、坐标、路线和缩放各自是否支持；自定义底图、点位详情、路线切换和实时位置分别确认|
|筛选/图表/实时看板|目录、事件及数据源都需存在；组件名称不证明筛选引擎、实时订阅或控制接口|

如果有render_ui，按当前schema选mode、组件及参数，不照搬别的部署的枚举或示例。需要的组件不在枚举中时，仅在当前工具文档明确支持其他接入方式后使用；否则说明缺口并降级。没有render_ui时不伪造可渲染JSON卡片。原生图片与文字不会因缺少动态组件而失去价值。

需求适配与可交付性分开：内容组织和用户操作决定采用哪种展示或交互；实际接口、资源和授权决定此刻能提供什么。暂时不可交付时，明确当前替代方案，而不是以一次故障否定需求的呈现价值。

确认和执行也分开：表单提交回传只代表收到用户值；工具结果确认的状态才可写入最终回复。草稿接收、预约批准、流程保存和流程执行是不同结果。未取得回执时明确哪些部分未完成，不虚构成功，也不否认已经确认收到的草稿。

display若依附最终回答而原生问题会阻塞当前回合，先完成图片/卡片展示，再收集确认，或选择已接通的同屏证据与确认模式。无图或图不可见时，不要求用户假装确认。

遇到生成/渲染失败，保留已知值、修订和附件；使用简明文字或原生问题完成可用部分，不重复同一失败调用。若没有可用的业务提交路径，明确保留草稿和未提交状态。降级不扩大业务权限，也不代替用户作不符合原要求的选择。

涉及表单按钮时，先读[按钮预设与回传](button-actions.md)。提交、保存、重置、跳过、放弃及继续新增等面向Agent的动作，应把意图与最新表单数据统一回传，由Agent决定下一步；链接导航及纯本地编辑另行处理。请求多个表单操作时，使用form_actions声明完整列表，由DSH生成独立同级按钮并统一绑定；不默认改为操作下拉框。仅在当前部署缺少此参数或确有失败且无法修正时说明限制并降级。

## 默认渲染与降级

命中正文中的简短文字、原生确认/补项、单图证据、静态地图、一次回执或用户指定格式等例外时，采用对应方式。其余已有足够事实且当前组件支持的需求，默认使用json-render，不把“没有交互”当成继续用纯文字的理由。较完整的报告、方案、分类资料、条目集合和多属性对照可用只读卡片、分区、表格或步骤展示。只需静态展示时不添加筛选器、切换、表单或按钮。

多项对照需传入真实条目和完整比较字段；报告/方案需传入概览、各部分事实、解释、证据和必要限制。按当前schema使用display，不能只传标题或一句摘要，让渲染服务补正文。界面能独立回答时可使用replace；必要解释留在文字中时使用supplement。按工具要求保留完整文字兜底，不以“界面已生成”代替答案，不向用户展示原始spec。

选用最简单的可用展示组件即可，不为使用json-render升级成整单编辑、流程控制或实时看板。已知缺少数据、组件、动作、资源或权限时先说明并澄清/替代，不用必然失败的调用试探，不发明接口。

已经调用而生成、渲染或资源展示失败时，本轮降级为完整文字或原生方式，并保留已有草稿、字段修改、对象及附件关联。只有存在明确可修正的诊断且工具允许时，才做一次有依据的修正调用；不能重复原请求、无限重试或轮换组件碰运气。仍失败或没有可操作诊断时直接兜底。界面失败不代表业务已提交或失败；分别报告已知的呈现状态与实际业务回执。

## 数据分析与Chart选型

对于已有真实数值的数据分析，当图表能更清楚地表达趋势、类别差异、排名或构成时，优先使用Chart并给出有依据的分析结论，不等待用户明确说“画图”。用户未指定图型时自行选择最贴合分析目的的一种，不单为图型偏好阻塞提问。用户指定方式仍优先；所需数据缺失、分析口径不明确或能力不支持时才澄清或采用可用替代。简短数值问答、单个指标及纯定性分析不为触发Chart而编造测量数据。

|分析目的|当前优先图型|条件|
|---|---|---|
|类别间数值比较、排名、不同组的同口径指标|bar柱状图|数值可比较、单位一致；比较排名时标签和值一起排序|
|时间序列的变化、走势|line折线图|保留真实时间顺序，标签与值对应，不把无序类别强连成趋势|
|同一整体内各部分的构成|donut环形图|仅一个序列，数值非负、合计大于0，各部分属于同一整体且口径不重叠|

当前已核实Chart仅支持bar、line、donut；不自造pie、scatter、heatmap等type。用户需要当前不支持的图型时说明限制，采用不歪曲分析目的的可用图或表格替代；不能把环形图称为已提供了指定的其他图型。不同量纲与定性属性混合的设备比较宜保留完整Table；可为价格等同口径数值附柱状图，不把价格、人数、距离和年限混成同一未说明尺度的数列。

工具schema支持时，在render_ui中列出components:["Chart"]以选择富组件目录，普通分析使用display；不要把bar/line/donut当成components名称。可将图表数据整理在business_data.chart等清晰位置，但这不是服务强制根路径。最终Chart.props使用type、可选字符串title、字符串数组labels、序列数组series；每个序列为{name:"指标名",values:[数值...]}。单位通过标题、序列名或配套说明表达，不向当前props添加未声明的unit、data或chartType。

当前labels为1—30个非空且不重复的字符串，series为1—5个名称不重复的序列，values为有限数值数组且长度与labels一致；donut只能有一个序列。labels、series及values按当前schema使用字面量数组，不用对象引用代替数组。Chart.series[].values中的元素必须是数值，不能套用Table单元格的字符串要求。具体数量及取值限制以当前部署schema为准；超限时按明确且说明的口径汇总或拆图，不静默截断。

标签、数值、单位和时间范围都取自已有材料；口径一致再比较。缺失不等于0，不擅自补0、插值或预测。计算占比、增幅或汇总时依据原始数值，并说明必要的计算口径及单位转换。图表与解读保留事实和推断的区别，不从走势直接宣称原因；没有真实数据就先澄清或做定性整理。调用时在user_query中加入所选图型及相关短类型约束，完整数据和分析依据仍放business_data。

Chart不替代必要的数字、约束、来源和结论，不能只给图而不回答分析问题。图表未覆盖的必要解释按工具约定用supplement保留；发生生成或展示失败时沿用一次有依据的修正及完整文字/表格降级规则，不反复试不同图型碰运气。

## 静态展示属性与绑定

业务数据可以包含对象、数组和数值；生成UI时必须逐属性服从当前组件schema。当前生成校验会先检查原始props，不能假定任何引用对象都会在检查前解析成字符串。即使{"$state":"/title"}最终可能指向字符串，将它直接放入只接受字符串的标题属性仍会失败。

|属性|当前要求|避免的写法|
|---|---|---|
|Section.props.title、description；Card.props.title|字符串，按schema可省略可选属性|整段业务对象、{text:...}、引用对象、null或{}|
|Steps.props.items|步骤对象的字面量数组|用一个引用对象代替整个items数组|
|Steps.props.items[].title、description|title为字符串，description为可选字符串|把整个步骤或绑定对象当标题/说明|
|Table.props.columns|字符串数组，如["型号","价格"]|Ant Design式的{title,dataIndex}列对象数组或引用对象|
|Table.props.rows|二维字符串数组，每行对应列顺序|业务对象数组、数值单元格或以对象引用代替行/表格|

向这些属性填写已提供的文本或明确的字符串叶字段。原数据为数值时保留business_data中的数值类型，向当前Table单元格写入时再按事实格式化为字符串；不把业务对象整体JSON.stringify成可见内容，也不补造金额、单位或结论。Steps每步title必须有事实来源；可选说明不存在时省略，不用{}或null占位。Table对齐列数与每行单元格数量，多种连接方式等列表可据原文合并成可读字符串。

只读说明、报告和比较没有必要为固定标题和正文增加动态引用。仅在当前schema明确允许相应表达式、状态来源正确且校验链路支持时使用。Text等其他属性可以有不同规则；Select.options、DynamicForm.fields、表单value和事件payload本来可能需要对象/数组，不能据此一概拍平或禁止绑定。可编辑表单仍须读取用户修改后的当前状态。

调用使用Section/Steps时，可在user_query附加：“Section标题、说明及Steps各项标题、说明使用字符串字面量，Steps.items使用数组，不使用引用对象。”使用Table时，可附加：“Table.columns是字符串数组，rows是按列对应的二维字符串数组，不用列定义对象或业务对象行。”按实际组件选择短约束，不把整份Skill塞入布局参数或挤掉必要布局信息；所有内容事实仍放business_data。

遇到invalid_props时区分类型问题与数据缺项：expected string, received object须检查是否误用整段对象、嵌套文本或状态引用；expected array须检查数组位置。仅拿到诊断、未见失败spec时，不声称已直接修复该spec；根据诊断约束一次修正请求，保留原事实。没有足够信息修正或仍失败时降级；不能把重试成功当作已定位先前对象的具体来源。

## 步骤条的适用范围

3个及以上有明确先后关系的操作步骤优先使用Steps；这是呈现偏好，不是任意列表的数量阈值。1—2步或用户明确要求简短文字时用文字；并列建议、事项清单和比较项不套用。步骤很多时保留内容和顺序，用分组、简短标题或纵向展示降低阅读负担，不为凑组件删掉步骤。

Steps是只读步骤序列，不默认提供执行、编辑、调序或业务提交。只要排好事项顺序的结果用文字；用户直接调整顺序并应用时考虑SortableSequence；编辑节点、参数或条件分支时考虑Workflow。不要为满足步骤条偏好生成流程编辑器或表单。

先根据真实材料组织步骤标题和必要说明，再调用render_ui；每步内容须进入business_data，不能只传标题让生成器补造。当前Steps使用props.items，每项为title及可选description、status，direction为horizontal或vertical，current表示当前步骤；具体参数以部署接口为准。Steps按当前工具说明走普通display即可，不向components添加未声明的Steps名称。

单纯讲解操作时，文案应明确是操作说明，不把默认高亮当成真实进度；不编造完成状态，也不擅自指定正在进行哪一步。只有任务实际提供进度事实时才设置相应状态。生成结果应保留全部步骤、先后关系和必要说明；无法交付组件时用完整文字步骤降级。

## 通用表单结构与自检

business_data保存真实业务数据和候选，user_query描述布局。组织通用表单时建议将字段定义集中在business_data.fields，其他业务对象、附件关联和稳定ID可保留在相应业务数据中；这是输入约定，不是服务对所有business_data强制执行的schema。最终DynamicForm的字段定义位于spec.elements.<表单ID>.props.fields。需要它时按当前工具说明选择表单mode与intent；DynamicForm不是可随意添加到components枚举的名称。

以下是当前已核实的DynamicForm字段约定；部署有不同接口时先查当前说明。字段使用type、key、label及可选value、disabled、placeholder；不向字段外层擅加options、default、required、rules、min或max。业务校验要求须使用实际支持的机制，不因把它写入业务数据就声称组件已执行校验。

|字段type|建议的value结构|注意|
|---|---|---|
|input|字符串|未知值可省略，不填造数据|
|inputNumber|数值|已知120写为120，不带货币符号或单位；不把未知金额补成0|
|date|日期字符串，如2026-12-10|仅使用已知日期，具体格式服从当前组件|
|daterange|{start_date:"2026-12-10",end_date:"2026-12-11"}|保存起止日期，不写成任意两元素数组|
|select|{options:[{value:"差旅",label:"差旅"}],default:"差旅"}|候选位于value.options，默认值是候选value|
|multipleSelect|{options:[{value:"投影仪",label:"投影仪"}],default:["投影仪"]}|默认值用数组，每项对应真实候选value|

表中的日期、金额和候选都是结构示例，不能变成用户事实。options每项须同时有字符串value和label；有实际业务ID时保留ID与显示名的区别。单选默认值用字符串，多选默认值用字符串数组；默认值来自已知选择且须属于候选。未选择时省略default，不为方便提交自选第一项。需要可选下拉时必须有真实候选；无候选时保留其他已知字段并澄清，或在业务允许时使用自由输入。

独立Select的候选位于props.options，props.value及绑定方式按其接口处理。不要向独立Select套value.options；也不要因为独立Select支持props.options就给DynamicForm字段加外层options。布尔确认等需求使用实际支持的原生问题或控件，不向DynamicForm自造checkbox等type。

调用前依次检查：

1. key非空且在本表单内唯一，沿用已有字段键和关联ID；type和外层键受当前组件支持。
2. value类型符合字段；选择字段options为非空对象数组，候选的value不重复，value和label均有事实来源。
3. default类型符合单选/多选，所有默认值属于候选，且没有把推荐项当成用户已选。
4. business_data保留真实字段、当前值、候选及附件关联；user_query不代替业务数据，不凭空补选项、金额或日期。

若能检查返回spec，再检查DynamicForm.props.fields中的候选与请求一致、默认值未丢失，提交读取当前绑定值而非初始快照。只有实际打开下拉或相应可见证据才能确认交互可用；拿到成功工具结果不代表已完成页面检查。

遇到unrecognized_keys或invalid_props，先区分是DynamicForm字段还是独立控件，再依据诊断的字段路径修正结构。未知外层options可能被严格schema拒绝，也可能在字段解析中丢失；而只剩value:"差旅"的选择字段即使通过schema，也可能显示默认值却没有候选。不要以删掉候选换取校验通过。按工具说明最多做一次有依据的修正调用；仍不可交付时保留数据并降级，不原样重试，也不向用户暴露协议诊断。

# 典型示例

这些是需求到呈现的参考，不是要求逐字复制的回答，也不承诺工具已实现示例中的业务能力。实际事实、选项和动作仍取自当前上下文。

## 文字例外之外默认渲染

“用两句话解释HTTP。”：命中简短解释例外，直接文字。“请确认是否选周三15点。”：原生确认。“草稿已接收，告诉我后续还要等什么。”：按真实状态给简短文字回执，不额外生成界面。

“根据提供的六款设备和五项属性，完整对比并给出取舍建议；只读展示即可。”：默认用json-render表格或分区展示，传入全部真实设备、属性和建议依据；不因为用户不需要点击就只给Markdown，也不额外添加筛选器。若只比较两个时段及一个差异，简短文字/Markdown通常足够。

“根据这些已给定材料，整理一份项目报告：概览、四组发现、对应证据和风险。”：默认用json-render分组展示完整报告，不需要用户额外要求卡片或交互；不可只生成标题摘要而丢失证据。必要解释未进入界面时保留文字并用supplement。用户对同一报告明确要求纯文字时遵从，不强制渲染。

“给三个事项排好，直接告诉我结果。”：短清单用文字；“把这三类资料的多条记录和详细说明整理成便于查看的页面。”：不属于短清单例外，默认用json-render展示；需要自主切换或展开时再选择Tabs/Collapsible。

“请实时跟踪设备位置。”但当前无定位数据或实时地图能力：先说明缺口，给可用的静态说明或澄清，不为满足默认偏好编造能力并试调。已知事实完整、组件可用时的实际渲染错误，则本轮保留全部内容并用文字/原生兜底；没有可操作诊断就不再次调用同一请求。

## 通用表单输入与选项位置

用户要求：“只收集费用草稿，费用类型候选为差旅、办公，已选差旅，金额120，让我核对修改后提交，不写入真实报销系统。”当前工具支持mode=form、intent=generic_filters时，可采用以下完整render_ui参数示例；字段键和示例事实应替换为本任务的真实数据：

```json
{
  "mode": "form",
  "intent": "generic_filters",
  "user_query": "根据提供的字段生成费用登记表，保留候选与已知默认值，让用户核对修改后提交草稿。",
  "business_data": {
    "fields": [
      {
        "type": "select",
        "key": "expense_type",
        "label": "费用类型",
        "value": {
          "options": [
            {"value": "差旅", "label": "差旅"},
            {"value": "办公", "label": "办公"}
          ],
          "default": "差旅"
        }
      },
      {"type": "inputNumber", "key": "amount", "label": "金额", "value": 120}
    ]
  }
}
```

这是工具调用参数，不是完整UI spec。business_data.fields是建议的事实整理方式；生成结果须将字段放在DynamicForm.props.fields，并有已接通的提交方式。这里不向components传入未声明的DynamicForm名称。用户把金额改为150后，应回传150和实际选择的类型；收到表单值只说明草稿已接收，不代表报销提交、保存或批准。

错误字段示例，不能照抄：

```json
{"type":"select","key":"expense_type","label":"费用类型","value":"差旅","options":["差旅","办公"]}
```

这个反例同时放错候选位置，并把候选写成字符串数组。应改成上方的value.options对象数组和value.default；不能只删除外层options，留下value:"差旅"就宣称可选。

如果业务提供稳定代码，独立Select的最终组件片段可以是：

```json
{"type":"Select","props":{"fieldKey":"expense_type","options":[{"value":"travel","label":"差旅"},{"value":"office","label":"办公"}],"value":"travel"}}
```

这个片段只说明独立Select的候选位置，不是完整可运行表单，也没有展示状态绑定。travel和office仅在业务实际提供这两个代码时使用；没有代码时不从示例杜撰ID。它的props.options不能搬到DynamicForm字段外层。

用户没有选择费用类型时，保留真实options并省略default。需要多选时使用multipleSelect及数组default。没有真实候选时，先询问候选来源，或在允许自由输入时用input，不编造“其他”等选项。完整字段规则见[表单结构与自检](capabilities.md#通用表单结构与自检)。

## 预约：咨询、填单和确认分开

用户：“周六下午带两位朋友来参观，要提前办什么？”

当前仅为简单咨询：用文字解释已知要求和未知项，不提前打开预约表。若要展示较完整的分组指南，可先用只读json-render；咨询不等于整单填写。用户随后要求填写并核对日期、时段、总人数和备注：使用DynamicForm预填同一草稿，让用户局部编辑后一次提交。缺失时段需要用户补充，不代填推荐值。

若仅询问“已满，17–18点或18–19点选哪个”，原生单选足够；不重填日期、地点、人数。若需要同时改日期、人数、设备并查看完整修订草稿，继续使用动态表单。用户拒绝下午则保持未提交。

表单已有明确“确认提交”按钮，点击后不再为同次提交追加原生确认。回执draft_received：“草稿已接收；正式预约结果尚未确认。”不将草稿接收说成提交未知，也不说预约获准。

## 报修：先看图，后进入业务表单

用户：“饮水机不出水，先拍一张给我看。”

取得照片后原生展示；没有拍摄能力或结果时说明缺口，不冒充已拍到。未来可能报修不是当前填单需求。

用户随后要求把三张照片放入反馈单，备注“昨天也这样”并补联系人：改用图片关联与DynamicForm，集中显示设备、地点、故障、备注、联系人和已有照片。保存各照片ID/关联，修改联系人不丢其他字段。提交后回到简短文字回执。

## 售后：整单编辑有价值

已给订单SO-2048、故障“无法开机”、联系人A和两张照片，用户要求联系人改B后核对提交：采用DynamicForm与附件预览。按明确修改预填B，仍允许用户核对；不额外收集没有业务必要的地址、电话或日期。

若用户指定只用文字，则以完整草稿和文字更正完成可用部分，不强制表单。若动态界面失败，需求仍适合表单；本轮以文字/原生收集降级，不据此改判该类需求永远适合文字。

## 简单确认与少量澄清

“是这个包裹吗？”：先展示候选图，再原生是/否确认。只有看过图的选择才有意义；不要让等待原生问题的回合把display图片挡住。

“线上还是线下？”：原生单选即可。推荐选项可以突出，但不等于用户同意。

“用途、人数、线上或线下先问清楚，只汇总不安排”：原生多题足够；一页轻量form也可，不把三题强行认定为复杂业务申请。

## 浏览、比较与图片

“先给三个套餐概览，再让我自己看各套餐限制”：Tabs/Collapsible适合自主切换和展开，不要求每次点标签都重新询问模型。

“只比较这四款，预算与重量条件都给定，解释推荐”：若只是简短固定比较，文字/Markdown即可；需要完整多字段对照、分项解释及推荐依据时，默认用json-render只读表格或分区展示。不因采用组件就声称有本地筛选；用户要自己改筛选条件后再核实是否有相应引擎。

两张左右图需要同时看：优先并列；三个视角需要按需逐个看：Tabs可选。不要把Tabs视为所有多图任务的默认答案。

## 多步骤操作说明

“教我完成设备报修：登记设备、填写故障、上传照片、提交申请，请逐步说明。”：四个操作步骤有先后关系，优先用Steps展示完整标题及已有的必要说明。business_data包含这四步，不凭空增加审批条件；文案说明这是操作指引，不声称用户已提交报修或已完成某一步。

“给我三个提高会议效率的建议。”：三条并列建议，用文字列表，不因超过两条就生成Steps。

“用一句话告诉我报修顺序。”：遵从一句话要求，用文字表达登记设备、填写故障、上传照片、提交申请的顺序，不强制生成组件。

“报修先登记设备，再提交申请，一共两步，解释一下。”：两步通常用文字；没有凭空增加第三步来触发Steps。

“让我调整三个参观展位的顺序，再应用新顺序。”：这是实际调序，核实能力后用SortableSequence；Steps不承担调序回传。

“让我编辑报修审批节点，加入材料不齐时补充再检查的条件分支。”：这是流程编辑，核实能力后用Workflow，不用只读Steps替代。

## 静态标题说明与表格类型

材料已给出“登记设备、填写故障、上传照片、提交申请”四步及下例中的说明。以下是最终spec示例，不是render_ui调用参数；标题、说明直接使用已知字符串，没有绑定整个对象，也没有设置虚假进度：

```json
{
  "root": "main",
  "elements": {
    "main": {
      "type": "Section",
      "props": {"title": "报修流程", "description": "以下为操作说明，不代表已执行。"},
      "children": ["flow-steps"]
    },
    "flow-steps": {
      "type": "Steps",
      "props": {
        "direction": "vertical",
        "items": [
          {"title": "登记设备", "description": "登记需要报修的设备。"},
          {"title": "填写故障", "description": "填写已知故障现象。"},
          {"title": "上传照片"},
          {"title": "提交申请"}
        ]
      }
    }
  }
}
```

错误属性片段，不能照抄：

```json
{"title":{"$state":"/steps/0/title"},"description":{"text":"登记需要报修的设备。"}}
```

即使引用可指向字符串，当前这些属性仍不接受该对象；按已有事实直接填写文本。说明未提供时省略可选description，不给每步编造详细操作。其他受支持的动态属性和可编辑表单绑定不受此例限制。

六款会议室设备只读比较时，把真实型号、价格、人数、拾音距离、连接方式及质保放入business_data，再要求生成器使用静态表格。当前Table的组件片段形如：

```json
{
  "type": "Table",
  "props": {
    "columns": ["型号", "价格", "适用人数", "拾音距离", "连接方式", "质保"],
    "rows": [
      ["A", "1200元", "4人", "2米", "USB", "1年"],
      ["B", "1800元", "6人", "3米", "USB、蓝牙", "1年"]
    ]
  }
}
```

这个片段只展示已给定A/B两行的结构，不是六款对比的完整答案；实际调用和生成必须保留A—F全部六行、各属性、约束和推荐依据。不能把columns改成[{"title":"型号","dataIndex":"model"}]，也不能把rows直接填成[{"model":"A","price":1200}]。预算2000元、一般6人的条件下，B满足人数且在预算内；A只标4人。16人、至少6米拾音条件下，E和F均满足已给参数；E较便宜，不据此推断音质或稳定性。若采用Section/Steps组织比较与建议，相关标题和说明同样使用字符串。

以上类型约束可简短加入user_query传给服务内模型。业务事实清楚而一次生成失败时，按具体诊断修正类型要求，最多一次有依据的修正；不原样重试，不改变预算、人数或产品参数来迁就错误结构。

## 排序、流程与单次改值

“给三个事项排好，直接告诉我结果”：文字有序列表。

“让我直接调顺序、试排，再保存”：SortableSequence，完整保留条目和稳定标识；应用后保留实际顺序。

“将日期改成周六，其他不变”：一次明确改值可用文字更新和必要确认，不必每改一个字段都重开表单。

“让我直接改报销节点，加材料不齐补充后返回检查的分支，期限3个工作日，然后保存草稿”：Workflow适合步骤、参数和分支整体编辑。文字说明完整路径，保存与真实执行分开；编辑图不保证业务逻辑自动正确。

## 地图和状态

“说明给定平面图的三个点和两段路线，只作静态示意”：已有原生地图图片+文字即可。

“我要点地点看详情并切换路线”：需求适合交互地图，但只有当前组件、事件与数据确实支持时才交付这些操作。若只有静态点位与缩放，说明缺口并给可用的静态图文/路线选择替代；不能把Tabs切换说明当成地图内路线切换已实现。

“失败时告诉我”“停一下”“继续”：单任务事件通知或控制回执优先文字。多个任务需要长期停留查看进度、历史和已接通的控制入口时，动态状态面板更适合；不凭界面按钮推定任务可被控制。

## 多按钮：意图与最新数据统一交给Agent

“重置、确认、跳过”使用form_actions声明reset、submit、skip三项，各自给忠实文案。DSH统一生成三个同级Button，共用form.submit回传意图与当前值；不生成操作下拉框，也不自造form.reset、form.confirm或form.skip。当前工具没有form_actions或明确失败无法修正时，才说明限制并保留全部意图的降级入口。

活动物资初始为折叠椅20把、联系人林晓，用户改成30把、联系人陈晨，再选择“恢复初始内容”：应回传reset及当前30把/陈晨，Agent根据可靠的初始快照重新生成20把/林晓的草稿；不能先在本地清空或恢复后只发送旧值。“恢复初始”与“清空本条”含义不同，范围不清时澄清，不把重置当作业务撤销。

用户已把联系人从A改B又选“提交后继续新增”：必须向Agent回传继续新增意图、B和已有照片关联；先完成本条要求的接收/保存，再由Agent生成下一份草稿。失败、未回传或保存未知时保留本条，不先清空。选择“保存草稿”也需意图与当前值一起回传，只有真实保存回执才称已持久化。

若用户想跳过而必填联系人为空：回传跳过意图与已知的部分草稿，由Agent决定继续哪一步；不能先伪造联系人让校验通过，也不把它说成完成登记。若当前独立按钮被校验阻塞，说明限制并改原生跳过，不声称未回传的编辑已经到达。

设备借用草稿要求“提交、查看规则、放弃”：form_actions声明submit与cancel两个独立按钮，规则使用用户给定链接；提交和放弃分别把实际意图及最新借用字段回传Agent；放弃只针对未提交草稿，不声称撤销真实借用记录。查看规则使用用户给定链接，不误提交当前草稿。纯本地展开、切换或字段编辑无需每次唤起Agent。详见[按钮预设与回传](button-actions.md)。

## 数据分析自动选择图表

“分析1—6月收入变化，单位万元，数据为10、12、11、15、18、20。”：用户没指定图型，模型自行选line展示时间趋势，并说明从10增至20、3月较2月回落、此后连续上升；不因没有原因数据就断言营销、季节或价格导致变化。当前工具支持Chart时，render_ui参数示例为：

```json
{
  "mode": "display",
  "components": ["Chart"],
  "user_query": "使用Chart折线图展示收入趋势，type为line；labels为字符串数组，series使用name和数值values数组，长度对齐。展示万元单位，并保留已有分析结论，不推断原因。",
  "business_data": {
    "chart": {
      "type": "line",
      "title": "1—6月收入（万元）",
      "labels": ["1月", "2月", "3月", "4月", "5月", "6月"],
      "series": [{"name": "收入（万元）", "values": [10, 12, 11, 15, 18, 20]}]
    },
    "analysis": ["收入由1月10万元增至6月20万元。", "3月较2月回落，此后连续上升。", "现有数据不足以判断变化原因。"]
  }
}
```

这是工具调用参数；business_data.chart是整理约定，生成器仍须把相应值放入Chart.props。不得只渲染曲线而遗漏必要结论，也不把示例数值当作其他任务的事实。分析说明未全部进入界面时保留文字并用supplement。

“对比甲、乙、丙三个部门销量，分别为120、90、150件。”：自行选bar比较类别；无需先询问用户想用什么图。“本月费用由差旅20万元、办公30万元、设备50万元组成。”：同一整体、非负且总额为100万元，可选donut展示构成，保留各项金额；若显示占比，明确按这100万元计算。

“分析六款会议室设备的价格、人数、拾音距离、连接方式和质保。”：这些属性有不同单位及定性内容，保留完整表格与选型依据；需要突出价格差异时可另加bar，不将所有属性混在一条数列中。“用一句话算一下本月比上月多多少钱。”：直接给有依据的简短计算，不强制Chart。

“分析项目延期原因。”但只有文字记录、没有测量数据：分组呈现事实、可能原因和缺失证据，不捏造概率或打分来画图。用户明确只要文字时遵从；指定当前不支持的scatter时说明能力限制，不编造type。出现负值的盈亏比较用适合的bar等方式，不用donut；缺失月份未提供数值时先澄清或明确缺失，不自动填0。

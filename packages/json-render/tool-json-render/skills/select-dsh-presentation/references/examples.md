# 典型示例

这些是需求到呈现的参考，不是要求逐字复制的回答，也不承诺工具已实现示例中的业务能力。实际事实、选项和动作仍取自当前上下文。

## 文字例外之外默认渲染

“用两句话解释HTTP。”：命中简短解释例外，直接文字。“请确认是否选周三15点。”：原生确认。“草稿已接收，告诉我后续还要等什么。”：按真实状态给简短文字回执，不额外生成界面。

“根据提供的六款设备和五项属性，完整对比并给出取舍建议；只读展示即可。”：默认用json-render表格或分区展示，传入全部真实设备、属性和建议依据；不因为用户不需要点击就只给Markdown，也不额外添加筛选器。若只比较两个时段及一个差异，简短文字/Markdown通常足够。

“根据这些已给定材料，整理一份项目报告：概览、四组发现、对应证据和风险。”：默认用json-render分组展示完整报告，不需要用户额外要求卡片或交互；不可只生成标题摘要而丢失证据。必要解释未进入界面时保留文字并用supplement。用户对同一报告明确要求纯文字时遵从，不强制渲染。

“给三个事项排好，直接告诉我结果。”：短清单用文字；“把这三类资料的多条记录和详细说明整理成便于查看的页面。”：不属于短清单例外，默认用json-render展示；需要自主切换或展开时再选择Tabs/Collapsible。

“请实时跟踪设备位置。”但当前无定位数据或实时地图能力：先说明缺口，给可用的静态说明或澄清，不为满足默认偏好编造能力并试调。已知事实完整、组件可用时的实际渲染错误，则本轮保留全部内容并用文字/原生兜底；没有可操作诊断就不再次调用同一请求。

## 奶茶预订：集中填单与简单补项

“我要给办公室的人预订奶茶。”：当需要填写饮品、数量、规格、冰度、糖度、配送时间等3项及以上相关业务字段时，优先用json-render动态表单集中收集，预填已知内容，允许统一核对修改后提交；不要连续弹出4—5次原生问题，也不因用户没有明确要求界面就逐项追问。字段依据实际下单要求确定，不将所有可能的字段都列为必填。需要多人不同饮品时，先核实当前表单能否表达条目，再保留各人/各条的关联。

门店菜单、规格和可选项来自已有材料；缺少菜单且饮品选择依赖它时，先取得材料或一次澄清关键来源，再展示真实候选。业务允许自由填写时可使用输入字段；不编造饮品、价格、库存或候选，也不默认声称可以向真实门店下单。草稿提交给Agent不等于真实订单已创建。

“这批奶茶是否确认下单？”：使用DSH原生确认，后续执行仍取决于实际授权和工具能力。“只补充冰度和糖度，其他已确认。”：两项简单独立信息可用一次原生提问收集，不重新填整单。“让我把整份奶茶订单一起检查修改。”：使用动态表单，保留已有值。用户明确要求逐步填写时按其偏好进行。

## 通用表单输入与选项位置

用户要求：“只收集费用草稿，费用类型候选为差旅、办公，已选差旅，金额120，让我核对修改后提交，不写入真实报销系统。”当前工具支持mode=form、intent=generic_filters时，可采用以下完整render_ui参数示例；字段键和示例事实应替换为本任务的真实数据：

```json
{
  "mode": "form",
  "intent": "generic_filters",
  "user_query": "根据提供的字段生成费用登记表，保留候选与已知默认值，让用户核对修改后提交草稿。",
  "business_data": {
    "fields": [
      {
        "type": "select",
        "key": "expense_type",
        "label": "费用类型",
        "value": {
          "options": [
            {"value": "差旅", "label": "差旅"},
            {"value": "办公", "label": "办公"}
          ],
          "default": "差旅"
        }
      },
      {"type": "inputNumber", "key": "amount", "label": "金额", "value": 120}
    ]
  }
}
```

这是工具调用参数，不是完整UI spec。business_data.fields是建议的事实整理方式；生成结果须将字段放在DynamicForm.props.fields，并有已接通的提交方式。这里不向components传入未声明的DynamicForm名称。用户把金额改为150后，应回传150和实际选择的类型；收到表单值只说明草稿已接收，不代表报销提交、保存或批准。

错误字段示例，不能照抄：

```json
{"type":"select","key":"expense_type","label":"费用类型","value":"差旅","options":["差旅","办公"]}
```

这个反例同时放错候选位置，并把候选写成字符串数组。应改成上方的value.options对象数组和value.default；不能只删除外层options，留下value:"差旅"就宣称可选。

如果业务提供稳定代码，独立Select的最终组件片段可以是：

```json
{"type":"Select","props":{"fieldKey":"expense_type","options":[{"value":"travel","label":"差旅"},{"value":"office","label":"办公"}],"value":"travel"}}
```

这个片段只说明独立Select的候选位置，不是完整可运行表单，也没有展示状态绑定。travel和office仅在业务实际提供这两个代码时使用；没有代码时不从示例杜撰ID。它的props.options不能搬到DynamicForm字段外层。

用户没有选择费用类型时，保留真实options并省略default。需要多选时使用multipleSelect及数组default。没有真实候选时，先询问候选来源，或在允许自由输入时用input，不编造“其他”等选项。完整字段规则见[表单结构与自检](capabilities.md#通用表单结构与自检)。

## 预约：咨询、填单和确认分开

用户：“周六下午带两位朋友来参观，要提前办什么？”

当前仅为简单咨询：用文字解释已知要求和未知项，不提前打开预约表。若要展示较完整的分组指南，可先用只读json-render；咨询不等于整单填写。用户随后要求填写并核对日期、时段、总人数和备注：使用DynamicForm预填同一草稿，让用户局部编辑后一次提交。缺失时段需要用户补充，不代填推荐值。

若仅询问“已满，17–18点或18–19点选哪个”，原生单选足够；不重填日期、地点、人数。若需要同时改日期、人数、设备并查看完整修订草稿，继续使用动态表单。用户拒绝下午则保持未提交。

表单已有明确“确认提交”按钮，点击后不再为同次提交追加原生确认。回执draft_received：“草稿已接收；正式预约结果尚未确认。”不将草稿接收说成提交未知，也不说预约获准。

## 报修：先看图，后进入业务表单

用户：“饮水机不出水，先拍一张给我看。”

取得照片后原生展示；没有拍摄能力或结果时说明缺口，不冒充已拍到。未来可能报修不是当前填单需求。

用户随后要求把三张照片放入反馈单，备注“昨天也这样”并补联系人：改用图片关联与DynamicForm，集中显示设备、地点、故障、备注、联系人和已有照片。保存各照片ID/关联，修改联系人不丢其他字段。提交后回到简短文字回执。

## 售后：整单编辑有价值

已给订单SO-2048、故障“无法开机”、联系人A和两张照片，用户要求联系人改B后核对提交：采用DynamicForm与附件预览。按明确修改预填B，仍允许用户核对；不额外收集没有业务必要的地址、电话或日期。

若用户指定只用文字，则以完整草稿和文字更正完成可用部分，不强制表单。若动态界面失败，需求仍适合表单；本轮以文字/原生收集降级，不据此改判该类需求永远适合文字。

## 简单确认与少量澄清

“是这个包裹吗？”：先展示候选图，再原生是/否确认。只有看过图的选择才有意义；不要让等待原生问题的回合把display图片挡住。

“线上还是线下？”：原生单选即可。推荐选项可以突出，但不等于用户同意。

“用途、人数、线上或线下先问清楚，只汇总不安排”：原生多题足够；一页轻量form也可，不把三题强行认定为复杂业务申请。

## 浏览、比较与图片

“先给三个套餐概览，再让我自己看各套餐限制”：Tabs/Collapsible适合自主切换和展开，不要求每次点标签都重新询问模型。

“只比较这四款，预算与重量条件都给定，解释推荐”：若只是简短固定比较，文字/Markdown即可；需要完整多字段对照、分项解释及推荐依据时，默认用json-render只读表格或分区展示。不因采用组件就声称有本地筛选；用户要自己改筛选条件后再核实是否有相应引擎。

两张左右图需要同时看：优先并列；三个视角需要按需逐个看：Tabs可选。不要把Tabs视为所有多图任务的默认答案。

## 多步骤操作说明

“教我完成设备报修：登记设备、填写故障、上传照片、提交申请，请逐步说明。”：四个操作步骤有先后关系，优先用Steps展示完整标题及已有的必要说明。business_data包含这四步，不凭空增加审批条件；文案说明这是操作指引，不声称用户已提交报修或已完成某一步。

“给我三个提高会议效率的建议。”：三条并列建议，用文字列表，不因超过两条就生成Steps。

“用一句话告诉我报修顺序。”：遵从一句话要求，用文字表达登记设备、填写故障、上传照片、提交申请的顺序，不强制生成组件。

“报修先登记设备，再提交申请，一共两步，解释一下。”：两步通常用文字；没有凭空增加第三步来触发Steps。

“让我调整三个参观展位的顺序，再应用新顺序。”：这是实际调序，核实能力后用SortableSequence；Steps不承担调序回传。

“让我编辑报修审批节点，加入材料不齐时补充再检查的条件分支。”：这是流程编辑，核实能力后用Workflow，不用只读Steps替代。

## 静态标题说明与表格类型

材料已给出“登记设备、填写故障、上传照片、提交申请”四步及下例中的说明。以下是最终spec示例，不是render_ui调用参数；标题、说明直接使用已知字符串，没有绑定整个对象，也没有设置虚假进度：

```json
{
  "root": "main",
  "elements": {
    "main": {
      "type": "Section",
      "props": {"title": "报修流程", "description": "以下为操作说明，不代表已执行。"},
      "children": ["flow-steps"]
    },
    "flow-steps": {
      "type": "Steps",
      "props": {
        "direction": "vertical",
        "items": [
          {"title": "登记设备", "description": "登记需要报修的设备。"},
          {"title": "填写故障", "description": "填写已知故障现象。"},
          {"title": "上传照片"},
          {"title": "提交申请"}
        ]
      }
    }
  }
}
```

错误属性片段，不能照抄：

```json
{"title":{"$state":"/steps/0/title"},"description":{"text":"登记需要报修的设备。"}}
```

即使引用可指向字符串，当前这些属性仍不接受该对象；按已有事实直接填写文本。说明未提供时省略可选description，不给每步编造详细操作。其他受支持的动态属性和可编辑表单绑定不受此例限制。

六款会议室设备只读比较时，把真实型号、价格、人数、拾音距离、连接方式及质保放入business_data，再要求生成器使用静态表格。当前Table的组件片段形如：

```json
{
  "type": "Table",
  "props": {
    "columns": ["型号", "价格", "适用人数", "拾音距离", "连接方式", "质保"],
    "rows": [
      ["A", "1200元", "4人", "2米", "USB", "1年"],
      ["B", "1800元", "6人", "3米", "USB、蓝牙", "1年"]
    ]
  }
}
```

这个片段只展示已给定A/B两行的结构，不是六款对比的完整答案；实际调用和生成必须保留A—F全部六行、各属性、约束和推荐依据。不能把columns改成[{"title":"型号","dataIndex":"model"}]，也不能把rows直接填成[{"model":"A","price":1200}]。预算2000元、一般6人的条件下，B满足人数且在预算内；A只标4人。16人、至少6米拾音条件下，E和F均满足已给参数；E较便宜，不据此推断音质或稳定性。若采用Section/Steps组织比较与建议，相关标题和说明同样使用字符串。

以上类型约束可简短加入user_query传给服务内模型。业务事实清楚而一次生成失败时，按具体诊断修正类型要求，最多一次有依据的修正；不原样重试，不改变预算、人数或产品参数来迁就错误结构。

## 排序、流程与单次改值

“给三个事项排好，直接告诉我结果”：文字有序列表。

“让我直接调顺序、试排，再保存”：SortableSequence，完整保留条目和稳定标识；应用后保留实际顺序。

“将日期改成周六，其他不变”：一次明确改值可用文字更新和必要确认，不必每改一个字段都重开表单。

“让我直接改报销节点，加材料不齐补充后返回检查的分支，期限3个工作日，然后保存草稿”：Workflow适合步骤、参数和分支整体编辑。文字说明完整路径，保存与真实执行分开；编辑图不保证业务逻辑自动正确。

## 地图和状态

“说明给定平面图的三个点和两段路线，只作静态示意”：已有原生地图图片+文字即可。

“我要点地点看详情并切换路线”：需求适合交互地图，但只有当前组件、事件与数据确实支持时才交付这些操作。若只有静态点位与缩放，说明缺口并给可用的静态图文/路线选择替代；不能把Tabs切换说明当成地图内路线切换已实现。

“失败时告诉我”“停一下”“继续”：单任务事件通知或控制回执优先文字。多个任务需要长期停留查看进度、历史和已接通的控制入口时，动态状态面板更适合；不凭界面按钮推定任务可被控制。

## 多按钮：意图与最新数据统一交给Agent

“重置、确认、跳过”使用form_actions声明reset、submit、skip三项，各自给忠实文案。DSH统一生成三个同级Button，共用form.submit回传意图与当前值；不生成操作下拉框，也不自造form.reset、form.confirm或form.skip。当前工具没有form_actions或明确失败无法修正时，才说明限制并保留全部意图的降级入口。

活动物资初始为折叠椅20把、联系人林晓，用户改成30把、联系人陈晨，再选择“恢复初始内容”：应回传reset及当前30把/陈晨，Agent根据可靠的初始快照重新生成20把/林晓的草稿；不能先在本地清空或恢复后只发送旧值。“恢复初始”与“清空本条”含义不同，范围不清时澄清，不把重置当作业务撤销。

用户已把联系人从A改B又选“提交后继续新增”：必须向Agent回传继续新增意图、B和已有照片关联；先完成本条要求的接收/保存，再由Agent生成下一份草稿。失败、未回传或保存未知时保留本条，不先清空。选择“保存草稿”也需意图与当前值一起回传，只有真实保存回执才称已持久化。

若用户想跳过而必填联系人为空：回传跳过意图与已知的部分草稿，由Agent决定继续哪一步；不能先伪造联系人让校验通过，也不把它说成完成登记。若当前独立按钮被校验阻塞，说明限制并改原生跳过，不声称未回传的编辑已经到达。

设备借用草稿要求“提交、查看规则、放弃”：form_actions声明submit与cancel两个独立按钮，规则使用用户给定链接；提交和放弃分别把实际意图及最新借用字段回传Agent；放弃只针对未提交草稿，不声称撤销真实借用记录。查看规则使用用户给定链接，不误提交当前草稿。纯本地展开、切换或字段编辑无需每次唤起Agent。详见[按钮预设与回传](button-actions.md)。

## 数据分析自动选择图表

“分析1—6月收入变化，单位万元，数据为10、12、11、15、18、20。”：用户没指定图型，模型自行选line展示时间趋势，并说明从10增至20、3月较2月回落、此后连续上升；不因没有原因数据就断言营销、季节或价格导致变化。当前工具支持Chart时，render_ui参数示例为：

```json
{
  "mode": "display",
  "components": ["Chart"],
  "user_query": "使用Chart折线图展示收入趋势，type为line；labels为字符串数组，series使用name和数值values数组，长度对齐。展示万元单位，并保留已有分析结论，不推断原因。",
  "business_data": {
    "chart": {
      "type": "line",
      "title": "1—6月收入（万元）",
      "labels": ["1月", "2月", "3月", "4月", "5月", "6月"],
      "series": [{"name": "收入（万元）", "values": [10, 12, 11, 15, 18, 20]}]
    },
    "analysis": ["收入由1月10万元增至6月20万元。", "3月较2月回落，此后连续上升。", "现有数据不足以判断变化原因。"]
  }
}
```

这是工具调用参数；business_data.chart是整理约定，生成器仍须把相应值放入Chart.props。不得只渲染曲线而遗漏必要结论，也不把示例数值当作其他任务的事实。分析说明未全部进入界面时保留文字并用supplement。

“对比甲、乙、丙三个部门销量，分别为120、90、150件。”：自行选bar比较类别；无需先询问用户想用什么图。“本月费用由差旅20万元、办公30万元、设备50万元组成。”：同一整体、非负且总额为100万元，可选donut展示构成，保留各项金额；若显示占比，明确按这100万元计算。

“分析六款会议室设备的价格、人数、拾音距离、连接方式和质保。”：这些属性有不同单位及定性内容，保留完整表格与选型依据；需要突出价格差异时可另加bar，不将所有属性混在一条数列中。“用一句话算一下本月比上月多多少钱。”：直接给有依据的简短计算，不强制Chart。

“分析项目延期原因。”但只有文字记录、没有测量数据：分组呈现事实、可能原因和缺失证据，不捏造概率或打分来画图。用户明确只要文字时遵从；指定当前不支持的scatter时说明能力限制，不编造type。出现负值的盈亏比较用适合的bar等方式，不用donut；缺失月份未提供数值时先澄清或明确缺失，不自动填0。
